# TabFurl

把浏览器窗口的标签页**收进**书签文件夹，也能把书签文件夹**还原**成带标签分组的窗口。

`furl` 是「卷起帆」，`unfurl` 是「展开帆」——这个名字说的就是它的两个方向：

| 方向 | 做什么 |
| --- | --- |
| 窗口 → 书签 | 当前窗口的标签，按标签分组存成书签文件夹，写进右栏**当前展示的那一层** |
| 书签 → 窗口 | 打开当前展示的那一层，按它的子文件夹创建对应的标签分组；标签先用**不加载**的方式打开 |
| 打开书签管理器 | 把当前这一层交给浏览器自带的书签管理器（`chrome://bookmarks/?id=<数字 id>`），在那儿看全貌、批量整理 |
| 收藏夹管理 | 在右栏里逐层浏览（双击进入、点面包屑退回），新建文件夹、改名、删除 |

**保存前可以挑。** 主界面按窗口顺序列出当前窗口的标签（分组是带缩进的块，未分组的标签就地插在中间），
逐枚勾选要存哪些再保存；整组也可以一键勾上。**默认一条都不选**（整窗存成书签是个很重的动作，
大多数时候只想要其中几条），勾选框有三态（全选 / 部分 / 全不选），所以一眼能看出「这个分组里选了没选全」。
每行的副文案是**完整网址**（不是主机名），`a.com/x` 与 `a.com/y` 不会再看着一样。
每行末尾的「打开」直接切到那一枚标签（跨窗口时会把那个窗口提到最前）。

**还原前也可以挑，但默认一个都不勾。** 勾选是跟着右栏展示的那一层走的；选好之后两种去向：
`← 打开`（**当前窗口**）、`＋ 新窗口`，要不要标签分组由下面的「**打开不建分组**」复选框决定。默认不勾是刻意的：还原是「要打开哪些」，
一下开着几十个标签页太危险；这一侧的默认状态与保存侧相反，是为了让「刚存完的」不会被下一次还原顺手打开。

**打开的标签默认不加载网页。** 一次还原几十个标签时，同时加载会把系统卡住，所以扩展等每个标签的导航提交后
把它卸载（`chrome.tabs.discard`）—— 标签仍在标签栏上，标题、位置、标签分组都在，点开哪一个才加载哪一个。
每个窗口会留一枚已加载的（活动标签无法卸载，这是 API 限制）。
所以**没点开的标签会是灰的**，那不是坏了。

**左栏会自己跟上。** 标签新建 / 关闭 / 移动 / 改名 / 换分组都会立刻反映到列表里，不用手动刷新。
两个面板各备了一个刷新按钮（左栏在全选框右边、右栏在按钮行的最右），留给「看起来不对」的时候——
书签树那边没有对应的事件（能在外面改它的只有浏览器自带的编辑器）。

> 「先等提交再卸载」是必需的，不是保守：`tabs.discard` 靠**已提交的地址**在激活时重新加载，
> 刚创建就问它会丢掉地址、标签变成 `about:blank`。代价是标签仍会发起首次请求（DNS、连接、响应头），
> 省下的是渲染、JS、子资源与内存那部分。

> 「当前窗口」指的是**主界面所在的那个窗口**（`chrome.tabs.query({currentWindow: true})`），
> 所以要在哪个窗口的位置上操作，就把主界面开在那个窗口里。

**只支持 Chrome（114+）**，不做 Firefox 兼容。Edge / Brave 等 Chromium 内核浏览器可直接加载同一个 `dist/chrome/`。

界面是一个独立标签页：等宽的两栏与中间一条窄操作列，**收藏文件夹**的 chip 栏在右栏表头下面一行。
**页面上没有标题块**——名字就在那个标签页的标题上（`TabFurl - 窗口 ⇄ 收藏夹`），省下的几十像素留给两个列表。

| 栏 | 做什么 |
| --- | --- |
| 左 · 当前窗口 | 按窗口顺序列出标签（分组是带缩进的块），逐枚勾选要存下哪些。**默认都不选**；每行末尾的「打开」直接切到那一枚标签 |
| 中 | 「存过去」与两个打开入口（当前窗口 / 新窗口），各自带当前勾选的数量；下面是「打开不建分组」复选框 |
| 右 · 收藏夹 | **一个可导航的浏览器**：双击文件夹进去，退路就是面包屑。当前这一层就是写入目标 |

**右栏顶端是收藏文件夹**：常去的那几层各占一个 chip，点一下就跳过去，chip 之间可以直接拖拽排序，
点 chip 上的 × 取消收藏。加收藏有两个**只有图标**的按钮：☆（把右栏现在这一层加进去）与
＋（打开一个**可搜索的文件夹列表**，打几个字就能缩到几行，↑↓ / Enter 可以全程用键盘）——
**只能收藏书签栏里的层**，扩展不往「其他书签」里写东西。
一个收藏都没有时会自动落在**书签栏**上，不会让你面对一个空面板。

右栏的行内操作：书签是「打开 / 修改 / 删除」，文件夹是「进入 / 改名 / 删除」，
**分隔线与间隔**是「转成另一种 / 修改 / 删除」，删除一律两步确认。
「＋ 新建文件夹」「＋ 分隔线」「＋ 间隔」「打开书签管理器」在框内顶部。
书签的「修改」会弹一个模态框（标题**与网址**两个字段），文件夹与两种记号因为只有标题仍是行内改名。

「打开书签管理器」直接把**当前这一层**在浏览器自带的管理器里打开（`chrome://bookmarks/?id=<数字 id>`，
管理器会把地址改写成 UUID 形式）。如果你的 Chrome **低于 155.0.8059.26**（例如 154.x），那一版有个已知
回归会让它退回默认层（[issue 565829425](https://issues.chromium.org/issues/565829425)），不是扩展的问题。

**两种组织记号是分开的**，因为它们本来就是给两种排版用的：

| 名字 | 网址 | 长什么样 | 给谁用 |
| --- | --- | --- | --- |
| 分隔线 | `separator.mayastudios.com/index.php` | 一枚竖线图标 | **横排**（书签栏那一排） |
| 间隔 | 同一个网址加 `?t=horz` | 一条通栏横线 | **竖排**（书签列表） |

两者都能在右栏里「转成另一种」（行内第一个按钮），转换只改网址、不动标题。

**支持直接拖拽**：左边一条标签拖到右边就只存这一条（落在某个文件夹行上就进那一层），
左边一个分组拖过去就建同名子文件夹存进去；反过来，右边的书签、文件夹或某种记号拖到左边就是打开它们。
从网页里拖来的链接落在右边会被按网址存成书签。中间的按钮只是拖拽的可点版本。
拖到某一栏的空白处时，提示是**最后一行下面的一条线**（写入总是追加到末尾），而不是把整栏涂亮。

写入目标是**右栏当前展示的那一层**，而收藏文件夹只决定**起点**（打开界面时落在第一个可用的收藏上）——
右栏可以自由走进书签树里任何一层，包括收藏**之上**的那几层。
扩展不会自己建文件夹，也不会往「其他书签」里写东西。
**每次保存都是往当前层追加**：同一个分组名会真的产生多个同名文件夹，不做合并、也不加序号。
代价是没有「会话」这一层——存两次分不出哪几条是这一次存的，也没有按时间的排序；
「撤销上次保存」只能撤销最近一次，而且**关掉界面就失效**（它靠内存里记下的 id）。

## 为什么不用浏览器自带的收藏夹

自带收藏夹做不到两件事：

1. 不能**把当前窗口存成一套结构**——它只能逐个页面手动收藏，分组信息丢失。
2. 不能**为多个收藏文件夹同时开标签页**——只能在书签管理器里来回切换。

TabFurl 只补这两块，不做通用收藏管理：书签树仍然是唯一存储，浏览器自带的收藏夹同步、搜索、导入导出全都照旧可用。

## 环境要求

- Chrome 114 或更高（实际绑定 API 是 `chrome.tabGroups` 的 89，版本号保守取高）
- Node.js >= 22.12（构建）；跑单元测试需要 >= 23.6
- pnpm

## 常用命令

```bash
pnpm install

pnpm watch          # 监视 src/ 与 pages/，改完自动重建 dist/chrome/（日常开发用这个）
pnpm build          # 生产构建 → dist/chrome/（混淆）
pnpm dev            # 单次开发用构建 → dist/chrome/（不混淆，报错堆栈可读）

pnpm test           # 单元测试（node:test）
pnpm typecheck      # tsc --noEmit
pnpm verify         # 产物自检（需先 build）
pnpm icons          # 重新生成 src/images/ 下的占位图标
```

构建产物在 `dist/chrome/`，可在 `chrome://extensions` 用「加载已解压的扩展程序」加载。

注意 `pnpm build` 要排在 `pnpm typecheck` 之前：`chrome` 全局类型与 `*.css` 模块声明的来源 `extension-env.d.ts` 由构建生成、不入库，新 clone 后直接跑 `typecheck` 会报一堆 `Cannot find name 'chrome'`。

## 在 Chrome 里加载

1. `pnpm build`（开发时用 `pnpm watch`）生成 `dist/chrome/`
2. 打开 `chrome://extensions`，右上角开启「开发者模式」
3. 点「加载已解压的扩展程序」，选 `dist/chrome` 目录
4. 点工具栏的 TabFurl 图标 → 主界面在独立标签页打开（已开着则直接切过去）
5. 改完代码：`pnpm watch` 会自动重建，回到扩展页点卡片上的刷新（↻），再重开主界面标签页

首次建议在右栏表头下面那行点一下 ☆（收藏右栏当前这一层），或点 ＋ 从列表里挑一个**书签栏**下的文件夹——
之后它就是一个 chip，点一下就能跳过去。扩展不会自己建文件夹，也不会往「其他书签」里写东西；
列表里没有合适的就先在书签管理器里于「书签栏」下新建一个，再点 ＋（它每次打开都会重读书签栏）。
**关于自动编译**：`pnpm watch` 会监视 `src/` 与 `pages/`，改完自动重建 `dist/chrome/`。
它**不启动浏览器，也没有热重载**——重建完仍需自己点扩展卡片上的刷新（↻），因为自动重载
要依赖独立的 Chrome for Testing（约 150 MB，`pnpm exec extension install chrome`）。
好处是产物的权限与生产构建完全一致，`pnpm verify` 照常通过。

**关于 `pnpm dev`**：它只是「不混淆的构建」，**不启动浏览器、也没有热重载**（名字取短是为了顺手）。
真正的 `extension dev` 没有做成脚本——它需要先下载独立的 Chrome for Testing（约 150 MB，
`pnpm exec extension install chrome`），换来的是热重载与一套控制桥；本项目不做自动化验收，
所以换成了「手动加载 + 点卡片刷新」，省掉一个重依赖。需要时仍可临时 `pnpm exec extension dev`，
但它会把 `dist/chrome` 覆盖成开发版清单（多出 `scripting` 与 `management` 权限，
`pnpm verify` 会失败），跑完要再 `pnpm build`。

## 测试

`pnpm test` 用 Node 内置的 `node:test` 跑 `src/shared/*.test.ts`，不引入任何测试框架：

- Node 原生执行 TypeScript，`tools/ts-hooks.mjs` 负责给源码里无扩展名的相对导入补 `.ts`。
- `chrome.*` 靠给 `globalThis.chrome` 赋值来打桩，不需要给产品代码加依赖注入。
- 覆盖的是命名规则、URL 判定、占位卡片转义、还原计划、窗口采集、设置读写这些之前没有测过的核心逻辑。

需要真实 Chrome 才能确认的部分（`chrome.tabGroups` 的实际行为、主界面与文件夹页的布局、跨设备同步后书签 id 变化）仍需手工测。
