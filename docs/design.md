# TabFurl 需求与初步方案

> 状态：骨架阶段。本文是需求范围与数据模型的唯一来源，代码与之冲突时以本文为准；要改范围先改本文。

---

## 一、背景

浏览器自带的收藏夹有两个做不到的地方：

1. **不能把「当前窗口」整套存下来。** 它只能逐个页面手动收藏，标签分组的名字与结构全部丢失，事后无法还原成原来的窗口。
2. **不能同时打开多个收藏文件夹。** 只能在书签管理器里一次次点进去，想并排对比两个分类做不到。

TabFurl 只补这两块。它**不做**通用收藏管理：新增标签、笔记、全文检索、失效链接检测都不在本项目范围内，这些交给浏览器自带的收藏夹（以及用户已有的同步、导入导出能力）。

## 二、目标与非目标

### 目标

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| F1 | 窗口 → 书签（可选范围） | 把当前窗口的标签按标签分组存进**存档根**（或其下的某个分组文件夹）。保存前可以逐枚勾选要保留哪些标签，整组也可以一键勾掉；也能只把**一条**标签或**一个**分组拖过去 |
| F2 | 书签 → 窗口（可选范围） | 打开存档根下的分组与散装书签，按它的**子文件夹（一层）**创建对应的标签分组；也可以逐枚勾掉不想打开的标签，或选择只开标签页、不建分组 |
| F3 | 文件夹启动器 | 打开存档根的阅读页，用于在标签页里浏览整套存档 |
| F4 | 存档管理 | 列出存档根下的分组与散装书签，支持展开／折叠、重命名、删除（两步确认） |
| F5 | 撤销 | 撤销最近一次保存（删除那一次新建的书签与分组文件夹） |
| F6 | 零网络 | 不申请任何 `host_permissions`，不发任何外部请求 |

### 非目标

- 标签、笔记、多维归类（那是另一个产品）
- 双向实时同步（三方状态冲突的成本远高于收益）
- 与思源等外部笔记软件的集成
- 自建存储：**书签树是唯一存储**，不引入 IndexedDB

## 三、书签树数据模型

```
📁 标签页存档                    ← 存档根：用户在书签栏里指定的一个已有文件夹
   ├── 📁 工作                    ← 标签分组（分组标题原文），多次保存会累加进来
   │      ├── 🔖 标题 A
   │      └── 🔖 标题 B
   ├── 🔖 标题 C                  ← 窗口里没进分组的标签，就地放成散装书签
   └── 📁 阅读
```

**没有「会话」这一层。** 每次保存都是往存档根（或某个分组文件夹）里**追加**，
不像早期版本那样每次保存先建一个带时间戳的会话文件夹。层级最多两层（分组 → 书签），
把窗口里的每个分组直接写成存档根下的一个子文件夹。三条结构规则：

- **存档根是书签栏里的一个已有文件夹，由用户在工具栏的「默认存档位置」里指定。** 扩展不建根文件夹、不往「其他书签」里写任何东西。
  **候选只来自书签栏**（`getBookmarksBarId()` 认 id `1`，认不出就报错），**绝不退化为「其他书签」**——
  存档位置只能来自用户的明确指定，扩展不替用户决定往哪里写；也不提供「自动创建存档根」「迁移旧存档根」这类动作。
  它挂在工具栏而不是某一栏里：两栏都要用它，塞进任一侧都会让另一侧看起来没配置。
  **它是「默认」而不是唯一**：它决定右栏的起点（打开界面时落在哪一层），而写入跟的是
  `viewFolderId`——右栏可能已经往里走了几层（见第七章的导航器）。
- **直接子级严格按窗口顺序排列。** 标签分组建成了子文件夹，窗口里没进分组的标签建成散装书签，**插在它们原来的位置上**——不会被集中挪到末尾，也不会有「未分组」这一层。窗口里一个分组都没有时，结果就是一列散装书签，所以「保存 → 还原」始终是对称的。
- **同名文件夹允许共存。** 书签树本来就允许同级同名（浏览器自己的收藏夹也允许），而且用户在不同窗口里可能真的有两个叫「工作」的分组，所以**不合并、也不追加 ` (2)` 序号**。
  代价是存档里可能出现多个同名文件夹，靠位置区分。

### 这样做的代价（三条已失去的能力）

没有会话层之后，下面三件事**永久消失**，不是待办：

1. **快照隔离**：存两次到同一个文件夹，两次的标签混在一起，再也分不出哪几条是这一次存进去的。
2. **按时间排序**：分组文件夹的名字是用户自己的分组名，没有时间戳；列表顺序就是书签树顺序。
3. **跨会话的撤销**：没有「刚建的那棵子树」可删，撤销只能是「删掉这一次新建的书签与分组文件夹」，
   所以它靠内存里记下写入时新建的 id 来实现（见 `SaveResult`）。**关掉界面就失效**——
   早期版本把会话 id 存进设置，那样重启后还能撤销；现在没有那个字段了。

取舍的出发点：把存档当「标签页池子」用（不断往里扔，需要时整包还原成窗口），而不是当「历史快照」用。

## 四、命名规则

命名只在 `src/shared/naming.ts` 里实现，界面层不得自己拼字符串。

| 层级 | 规则 | 示例 |
| --- | --- | --- |
| 存档根 | **不由扩展命名**：用户在书签栏里指定一个已有文件夹 | `标签页存档` |
| 分组 | 分组标题原文 | `工作` |
| 空标题分组 | `未命名分组（蓝）`，用颜色消歧 | `未命名分组（蓝）` |
| 手动新建的文件夹 | 默认 `新建文件夹`；同理同名共存，只避开「同一层里完全同名的默认名」 | `新建文件夹 2` |

新建的文件夹建在**右栏当前展示的那一层**，不是存档根。

> 上表就是**写进书签的实际形态**：`sanitizeFolderName` 只做控制字符、空白与长度这三件事，
> 不动任何可打印字符（见下面的清洗规则）。

**没有会话命名这回事。** 早期版本会给每次保存产生一个 `名字 · 2026-10-02 14:30` 的会话文件夹，
于是命名层要千与时间戳拼名字、按预算截断、重名去重。取消会话层之后这些全部消失：

- **没有时间戳**：分组文件夹的名字是用户自己的分组名，不需要排序保险。
- **没有自定义会话名**：输入框、预览行与 `formatSessionName` 一起删了。
  顺带记一下那个本来就不可能的需求：「窗口自定义命名」——`chrome.windows.Window` 根本没有
  `title` / `name` 字段，Chrome 也不提供这个功能。
- **没有去重**（`dedupeName` 已删）：同名允许共存，见第三章。

**清洗规则**（`sanitizeFolderName`）：

1. 去掉控制字符（`\u0000-\u001f`、`\u007f`）
2. 折叠连续空白为一个空格，并去掉首尾空白
3. 截断到 100 字（截断处再去尾随空白）

**可打印字符一律保留原文**，包括 `/ \ : * ? " < > |`。Chrome 不禁这些字符（`create()` 的
`title` 就是个普通字符串，官方文档没写任何禁用字符或长度上限），所以不做替换。
早期版本会把它们换成 `_`，那是为「导出为文件路径」提前挡 Windows 的非法字符；
**那个功能没有做，规则随之删掉**（依据：不为没实现的功能付出改名的代价）。
真要做导出时再补，届时还得处理 Windows 的保留设备名（`CON`、`NUL`、`COM1`……）与不能以点结尾两条。

## 五、还原规则

| 输入 | 行为 |
| --- | --- |
| 子文件夹 | 建一个同名标签分组（关掉「建分组」时跳过这一步） |
| 子文件夹里的书签 | 打开标签并归入该分组 |
| 存档根顶层的散装书签 | 打开成**未分组**的标签，位置按它们在文件夹里的次序 |
| 被勾掉的书签 | 不打开；因为它而空掉的分组也不创建 |
| 子文件夹里的**子文件夹** | **跳过**（只处理一层），数量计入 `skipped` 并在界面显示 |
| 浏览器内部页面 | 跳过，计入 `skipped` |
| 分隔线（占位书签） | 跳过，不为它打开标签；**不计入 `skipped`**（它不是「丢了东西」） |

因为恢复时是**按存档根的子级顺序**依次开标签的，还原出来的标签次序与保存时一致：未分组的标签会回到它们原来的位置，而不是被堆到末尾。

#### 书签分隔线

Chrome 早已不支持书签分隔线，社区的做法是收藏一个**指向固定网址的书签**来模拟
（`https://separator.mayastudios.com/index.php`，判定见 `urls.ts` 的 `isSeparatorUrl()`）。
TabFurl 把它当成书签树里的组织记号，而不是一个页面：

- **阅读页**把它画成一条横线，横跨整个网格；条目标题非空时就是分隔线标题，嵌在线的正中（「—— 标题 ——」）。
  标题**首尾的 `─` 会被剥掉**（`separatorTitle()`）：很多工具把标题写成 `──── 工作 ────`，那两道横杠是手画的线，
  而我们已经用 CSS 画了线，留着就成了第二条——长度写死、跟容器宽度对不上。剥的时候把**空白当成同一类字符一起剥**，
  所以 `─ ─ ─` 这种用横杠加空格拼出来的假线会整条消失，退化成只有一根线的形态（正是想要的）。只动首尾：
  `2020 ─ 2024` 中间那根是标题的一部分。
  真实数据（306 枚 `?t=horz` + 4 枚无查询串）里，17 种标题都是「教程────────────」这种**尾随**横杠，剥完得到 `教程`；
  判定与清洗对全部 310 枚**零误伤、零漏网**。
- **它保留原位**，所以阅读页的子级只能有**一个**网格：文件夹卡片、书签卡片、分隔线三类子级按书签树顺序依次排下去，
  分隔线靠 `grid-column: 1 / -1` 横跨整行。早期版本把「子文件夹」与「未归入子文件夹」拆成两段渲染，
  于是分隔线全被推到列表末尾——而用户放这些线就是为了把相邻的几组文件夹隔开，位置一丢，线就只剩装饰作用。
  代价是两段节标题没了，概览靠页首的「N 个子文件夹 · N 个书签」一行。
  存档面板那一侧本来就是保序的（`archiveChildren` 与文件夹内的 `.kids` 都按数组顺序渲染）。
- **它不算书签**：阅读页的「N 个书签」、子文件夹卡片上的枚数、`FolderOption` 的两个计数，以及存档面板的
  「打开（N）」与文件夹副文案都不含它；它也没有勾选框（勾选维度是「要打开哪些标签」，它不是其中之一）。
  书签树那一侧的判据是 `isRealBookmark()` / `realBookmarks()`（`shared/bookmarks.ts`），
  **不能用「有没有 url」代替**：渲染要画分隔线、计数要跳过它，用同一个写法就只能对一头。
  漏一处的症状：右栏「打开（N）」多算，而且全选框按这份名单算总数，会被永远勾不上的项拖在「部分选择」上，
  点了全选也回不到「全不选」。
- **不参与还原**，也就不会多出一个无用标签。

判定按**主机名 + 路径**，忽略协议、查询串与片段：同一个记号在不同工具、不同时期会写成
`http` / `https`，也可能带上 `?t=horz`、`?title=…` 之类的参数。只认该域名下的 `/index.php`
（以及省略路径后被浏览器补成 `/` 的写法）——不能只认主机名，那会把该域名下的任意页面也当成记号。

实现分两处：阅读页 `pages/folder.ts`（`separatorMarkup` / `entryMarkup`），
存档面板 `src/app/TransferPanel.ts`（`archiveBookmarkRow` 里分出 `.divider`）。
两边共用 `restore.ts` 的 `PlannedBookmark.separator`：分隔线照常留在 `planRestore()` 的计划里
（界面要按**原位置**画出来），只有真正的标签才走 `restorableBookmarks()`。
只含分隔线的分组等于空分组，不产生项。

还原目标窗口**由按钮直接决定**，不是存起来的偏好：打开标签去哪里属于「这一次要开到哪里」，
同一个存档两次可能选得不一样。主界面中间那列与阅读页各给出自己的入口：

| 入口 | 去哪 | 建不建分组 |
| --- | --- | --- |
| `← 打开` | **当前窗口** | 按子文件夹建分组 |
| `＋ 新窗口` | 新窗口 | 按子文件夹建分组 |
| `只开标签页（不建分组）` | 新窗口 | 不建 |
| 阅读页的「还原到新窗口」/「还原到当前窗口」 | 对应窗口 | 按子文件夹建分组 |

它打开的是**右栏当前展示的那一层**（`viewFolderId`），不是无条件打开存档根。
新窗口通过第一个标签顺手创建，避免先开空窗口再补标签的闪烁。

`← 打开` 走当前窗口而不是新窗口：它与 `＋ 新窗口` 是同一件事的轻重两档，
而「打开」这个动作在多数时候是「接着现在这个窗口用」。把几十个标签塞进当前窗口是不可撤销的，
所以另一档（新窗口）必须有一个同样显眼的按钮，而不是藏在别处。

`groupTabs: false` 是「只开标签页」：同一份计划，只是不建分组（子文件夹的名字丢掉）。

**打开的标签默认不加载**（懒加载）。

`chrome.tabs.create()` **没有**「先不加载」这个选项——传了 `url` 就会立即开始加载，
`active: false` 只是不聚焦，所以一次还原几十个标签会造成瞬时并发加载而卡顿。
真正能做这件事的是 `chrome.tabs.discard()`（Chrome 54+）：从内存卸载，但标签仍在标签栏上
（标题、位置、标签分组都保留），点开时才重新加载。

三条实现要点：

1. **舍弃必须放在建分组之后**。分组、窗口都完成了，标签的位置与归属已固定，此时卸载最安全。
2. **活动标签无法被舍弃**（API 限制：`tabs.discard` 对活动标签不生效），所以每个窗口会留一枚已加载的。
   这正好让人看得见窗口确实开出来了。
3. **舍弃失败不能拖垮整次还原**：标签已经打开了，只是会真加载而已，所以逐个 `try/catch` 只记日志。

#### 必须先等导航提交，否则标签会变成 about:blank

**这是实测到的 bug（2026-10-03），不是理论风险。** `discard` 的语义是「卸载已加载的内容，
激活时按记录的地址重新加载」；如果标签还在加载、没有任何**已提交**的地址，Chrome 就没有可恢复的地址，
标签会落到 `about:blank`。

判定依据就在 `Tab` 的文档里：`Tab.url` 是「主框架的**上次已提交**网址……**如果标签页尚未提交，
则可能为空字符串**」，而目标地址只出现在 `Tab.pendingUrl` 里。所以「刚 `create()` 完就 `discard`」
必然丢掉地址——`create()` 返回时导航还在路上。

因此现在轮询到 `Tab.url` 有值（且 `pendingUrl` 已清空）才动手：

- 每 50ms 查一次，最多等 2 秒。整体是**同步等待**的，所以超时上限直接决定状态栏会卡多久。
- **超时就干脆不碰那枚标签**，让它照常加载。即「宁可少省点内存，也不能把标签弄成空白页」。

代价要说清楚：等待提交意味着**每个标签仍会发起首次请求**（DNS、连接、响应头）。
省下的是最贵的那部分（渲染、JS、子资源、内存），省不掉网络往返本身。

**反馈只在需要时出现**：「正在打开…」留在进行中（必须留：舍弃前要等导航提交，最长 2 秒，
没有它界面看起来就是卡住的）；失败时给出错误；**成功后不留报账式提示**（标签/窗口已经打开，
看得见；要打开多少在点之前就写在按钮上了）。

**勾选与计数共用一条通路。** 界面渲染的清单与还原用的计划都是 `restore.ts` 的 `planRestore()`，
界面再把勾掉的书签 id 交给 `applyExclusions()`；所以「看到几枚就会开几枚」不靠人工对齐，而是同一份数据。

## 六、平台与权限

**目标浏览器只有 Chrome**（最低 114，写在 `minimum_chrome_version`）。不做 Firefox 兼容。

这带来了实质简化，不是单纯的偷懒：

- `chrome.tabGroups`（89+）可以直接调用，**不需要特征检测与降级分支**。
- MV3 下 `chrome.*` 原生返回 Promise，**不需要 `webextension-polyfill`**，也不需要维护 `browser.*` / `chrome.*` 两套类型。
- 清单是纯 MV3，**没有任何 browser-prefixed 字段**，减小了一半（含 `browser_action` / `sidebar_action` 的 MV2 形态）。

| 权限 | 用途 |
| --- | --- |
| `bookmarks` | 读写书签树 |
| `tabs` | 读取标签标题 / URL / 分组，创建标签 |
| `tabGroups` | 读取分组标题与颜色、创建分组 |
| `storage` | 保存设置 |
| `favicon` | 用 `_favicon` 端点取网站图标；**读 Chrome 本地缓存，不发网络请求**。已申请 `tabs`，所以它不额外产生权限警告（官方文档明确：只有尚未申请 `tabs` 或主机权限时它才警告） |
| `host_permissions` | **无** |

图标就一张真图标（22px），没有底色或首字母。`_favicon` 的实测行为（2026-10-02 在真实 Chrome 里验证）：
**它从不失败**——缓存里有就返回真图标，没有就返回**默认地球**，连根本不存在的域名也返回 32×32 的图片
（`onerror` 不触发）。所以代码里不需要失败处理：产物要么是真图标、要么是地球，不会出破图。
代价要说清楚：**没有图标的站点会长成一个样**，一排全是地球。
不请求 Google 的 favicon 服务，也不把 `tabs.Tab.favIconUrl` 拿来渲染——后者指向网站服务器，
渲染时等于向该站点发请求。

> 如果将来要支持 Edge / Brave 等 Chromium 内核浏览器：不用改代码，直接加载 `dist/chrome/` 即可（它们共用同一套 API）。只有要支持 Firefox 才需要重做上面这几层。

依赖方向单向：`pages/` → `src/app/` → `src/shared/`。**`shared/` 不得 import 任何界面模块**。
存档位置选择器不是面板：它不读 `AppEvents`，而是**触发** `settingsChanged`（选中即落盘）。

界面只有一个页面（外加阅读页）：

- `pages/app.html` —— 主界面，点工具栏图标以**独立标签页**打开（已开着则切过去，不重复开）。
  工具栏一行是**默认存档位置**选择器，下面是等宽的两栏与中间一条窄操作列：
  - **左：当前窗口** —— 按窗口顺序列出标签（分组是带缩进的块，未分组的标签就地在原位），逐枚勾选要保留哪些。**默认全选**。
  - **中：两个方向** —— 一个「存过去」，三个打开入口：`← 打开`（当前窗口）、`＋ 新窗口`、`只开标签页（不建分组）`，各自带当前勾选的数量。
  - **右：存档** —— **一个可导航的浏览器**：双击子文件夹（或点「进入」）进去，`↑ 上一层` 与面包屑退出来。
    当前的这一层就是**写入目标**（「存过去」「新建文件夹」「拖到空白处」都落在它里面）。
    子文件夹行带三态勾选框（=「它里面那一层书签」）、改名、删除（两步确认）。**默认全不勾**。

### 为什么右栏是可导航的浏览器，而不是可展开的树

早期版本把存档列成一棵可以「全部展开 / 全部折叠」的树，子级用缩进链表达层级。它有两个问题：

1. **深入到第三、四层时，缩进链会把面板压成一条细缝**，每一层都在抢横向空间，而收获只是「看到了下级」。
2. 根节点的子级通常是二十几个文件夹，展开后的信息量远超一屏，用户实际能做的仍然是一层一层看。

改成导航器后，**「上一层」是 O(1) 的退路**，横向空间不再随深度衰减；面包屑又把「我在哪」当场告诉你。
这不是一个「更好看的树」，而是一个不同的交互模型：树在回答「整体长什么样」，导航器在回答「我现在在哪、能往哪去」。

代价与取舍：

- **勾选是跟随展示层级的**。换一层就换成那一层的选择，不会把别处的勾选默默带过来。
  这是刻意的：若保持全局勾选不变，主页顶部的「已选 N / N 枚标签页」会与眼前的列表毫无关系——
  正是「列表看着全选、按钮说没选中」那类错觉。要看全貌、要按整棵树打开，用「打开阅读页」。
- **文件夹行的勾选框仍然保留**，含义是「它里面那一层书签全要 / 全不要」（与 `restoreFolder` 的口径一致：
  它只处理一层：子文件夹建分组、散装书签不建分组）。所以**进不进去与勾不勾它是两件事**：
  进去是「往它里面存东西 / 接着往下看」，勾上是「打开它里面的书签」。
- **存档根以上的层不可导航**：面包屑把完整路径画出来只作上下文，只有存档根及以下可以点。
  否则「存过去」会把东西写到用户指定范围之外。

### 为什么不分 Tab，以及为什么是两栏

早期版本把它拆成「保存」「存档」两个 Tab。两者实际上是**同一个东西的两侧**：
左侧是一个尚未落盘的会话（标签还住在浏览器里），右侧是已落盘的会话，
数据结构同形——都是有序的「分组 | 标签」序列（即 `WindowChild` 与 `planRestore()` 的产品）。

分 Tab 的真实代价不是「多一次点击」，而是**保存完看不见它落在哪**：
想确认或直接还原刚存的那一套，得先切过去。每二条是「撤销上次保存」只在保存侧出现，
而它要撤销的那一项此时正显示在另一侧。

为什么要两栏（而不是更炫的方案）：**两份清单无法共享同一列高度**。
实测过几种做法：

| 方案 | 结果 |
| --- | --- |
| 草稿置顶 + 下方存档（用 `sticky`） | **不可行**：粘性元素一旦高于滚动容器，受「容器边界」约束就钉不住，会跟着内容一起滚走 |
| 草稿/存档互斥展开（一张手风琴） | 可行且干净（同时刻只有一块列表、一条滚动条），但「保存」入口被收起时只剩一行，少一个随时可用的落点 |
| **并排两栏（采用）** | 两栏各自滚，页面不滚；两个方向始终可见；与拖拽天然契合 |

两栏等宽是刻意的：哪一边更宽都在暗示「哪一边更重要」，而它们同等重要。

工具栏上那个选择器叫**「默认存档位置」**而不是「存档位置」：它决定的是**起点**——
打开界面时右栏落在哪一层、以及不导航时写入哪里。右栏一旦往里走，「存过去」跟的是当前那一层。
叫「存档位置」会让人以为只能存这一个文件夹（而右栏的双击进入就与此矛盾了）。

### 拖拽

拖拽不是另加的功能，而是同一件事的**精确版**：

| 拖动 | 落到哪 | 行为 |
| --- | --- | --- |
| 左栏一条标签 | 右栏（空白处） | 只在存档根下存这一条 |
| 左栏一条标签 | 右栏某个**分组文件夹行** | 存进那一层 |
| 左栏一个分组 | 右栏 | 建同名子文件夹存进去（落在文件夹行上就再进去一层） |
| 右栏一条书签 | 左栏 | 打开这个页面 |
| 右栏一个文件夹 | 左栏 | 把它里面的书签全打开（不建分组） |
| 从**网页**拖来的链接 | 右栏 | 按网址存成书签（零额外代码：载荷就是 `text/uri-list`） |

两个实现要点：载荷带一个自有的 `application/x-tabfurl`（`DRAG_TYPE`）用来区分「内部拖动」与
「外部链接」；`dragover` 里只能读到 `types` 而读不到 `data`（浏览器的安全限制），
所以另用一个变量记住「正在拖什么」来决定收不收。

**勾选只有一个维度：一枚标签要么会被还原、要么不会。** 存档行与分组行都是它上面的聚合（三态），
所以不会出现「展开后看着全选、但按钮说没选中」这种自相矛盾。

**两边的默认值相反，这是刻意的：**

| 位置 | 默认 | 为什么 |
| --- | --- | --- |
| 保存（窗口 → 书签） | **全选** | 保存的语义就是「把当前窗口收起来」，少数不想存的手动取消 |
| 存档（书签 → 窗口） | **全不勾** | 还原是「要打开哪些」，默认全开太危险（可能一下几十个标签页）；且存完的新存档也不会被下一次还原顺手打开 |

存档侧仍然用**排除集**而不是选中集，配合一份「见过的书签 id」：没见过的默认算排除。
这样既做到「默认不勾」，重渲染又不会弄丢用户已做的勾选（换成选中集会两头都不讨好）。

顶层、两栏的分组层都反映它下面的实际勾选：

- **顶层按标签聚合**，不按「有几个文件夹还有东西」——否则「已选 4 / 5 枚」会显示成全选。
- **按钮上写数量**（`存过去（5）` / `打开（2）`）：得让人在点之前看见这一下会写入或打开多少。
- **副文案以「已选」为主**：打开侧默认不勾，若直接写「N 个标签」，默认会显示成「0 个标签」，
  看着像这个存档是空的。所以顶层写作 `尚未勾选（存档里共 3 枚标签页），勾选后才能打开` 或 `已选 2 / 3 枚标签页`。

点击的语义是：全选 → 全不选，部分 / 全不选 → 全选（不沿用原生「把 checked 取反」，
那会让部分状态变成全不选，与惯例相反）。顶层与分组层用同一套规则。

主界面不放在 `src/` 下而放 `pages/`：它不再由清单（`side_panel`）引用，而 `pages/` 正是构建工具
为「未被清单声明的 HTML」设的特殊目录，产物路径即 `pages/app.html`。
- `pages/folder.html` —— 文件夹阅读页，由 `?id=<folderId>` 指定文件夹；与主界面同属 `pages/` 特殊文件夹机制。
  顶部面包屑（`书签 / 书签栏 / 临时 / … / 当前层`）**除当前层外都可点**，点了就打开那一层文件夹；
  当前层是这一页自身，做成链接只是噪声。根节点的标题在书签树里是空串，所以统一兜底成「书签」
  （兜底做在 `getNodePath()` 里，面包屑、`<h1>`、页签标题共用同一个值，不会出现「面包屑有字、标题空白」这种不一致）。

## 八、关键约定与已知取舍

1. **书签 id 是设备本地的。** 跨设备同步后 id 会变，因此任何持久化数据都不能把书签 id 当作跨设备稳定的标识。现在**唯一**存进设置的 id 就是 `archiveRootId`，重建代价是用户重新选一次文件夹。
2. **同一 URL 可以出现在多个文件夹。** 存档不做去重——多次保存同一个窗口会真的多出几份；写入前也不扫已有内容（扫的话每次保存都多一轮读取）。
3. **分组颜色不往返。** 书签文件夹存不下颜色，还原时分组用浏览器默认色。`TabGroupColor` 只在「空标题分组用颜色消歧」时使用。
4. **写入是逐条 `await` 的。** 一百个标签就是一百次 IPC，第一次保存会有明显停顿。批量优化的预留位置在 `capture.ts` 的 `writeTabs()`。
5. **深色模式**靠 `prefers-color-scheme`，不维护两套主题。
6. **散装书签的位置以「分组的第一个标签」为界。** Chrome 的标签栏里同一分组的标签必定连续，所以窗口总是「未分组段 / 分组 / 未分组段 …」的交替；按 `TabSnapshot.index` 归并就能如实重建这个次序。隐含的另一面是：文件夹层级无法表达「把某个未分组标签插在同一分组的两个标签之间」——但那种布局在 Chrome 里本就不存在。
7. **撤销是内存态的，且顺序不能反。** 没有会话层之后，撤销只能是「删掉这一次新建的书签与分组文件夹」，
   id 在写入时收集（`SaveResult.folderIds` / `bookmarkIds`），**只存在内存里**：关掉界面就失效。
   删除时**先删书签、再删文件夹**：反过来会连书签一起删掉，让后面的 id 全部失效。
   只撤销**最近一次**写入，而不是「这一轮界面里所有写入」——拖拽会让一次会话里出现很多次写入，一次全清会吓到人。
8. **还原时散装书签不建分组。** 早期版本有个「为未分组书签也创建分组」的开关，它会把分散在各处的标签收进同一个 `未分组` 分组，与「保持原位」直接矛盾，已随穿插方案一起移除。
9. **主界面只允许有一个滚动容器，且用满整页宽度。** 主界面是「一屏的应用」：`.app--shell` 把整页锁在一屏内（`100dvh`）
   并取消 `.app` 的 `--content-max` 上限，滚动交给两栏各自的 `.box`（`flex: 1; min-height: 0; overflow-y: auto; overflow-x: hidden`）。
   于是顶栏与底部按钮始终在视野里。**不要给列表加 `max-height`**——那会与页面滚动叠成两条滚动条，
   而列表一长，底部按钮就被推出屏幕，得先滚到底才能点（旧版就是 `42vh` / `52vh` 各写一个）。
   宽度上限单独留给阅读页：那边是一篇文章，行宽需要收着。
10. **两栏的 grid 轨道下限必须是 `0`。** `minmax(0, 1fr) auto minmax(0, 1fr)` 里的 `0` 不能省：
   默认的 `1fr` 等价于 `minmax(auto, 1fr)`，那个 `auto` 下限是子项的 min-content 宽度，
   而两栏里都是一列不换行的标题，于是列表的 min-content 就是最长那条标题的宽度
   （实测左栏 422px、右栏 364px）。窗口一窄，两栏之和超过可用宽度，整页就被顶出一条横向滚动条。
   实测 1000px 宽时两栏已经卡在 426/426 不再变窄，900px 起 `scrollWidth` 固定为 918px。
   改成 `minmax(0, 1fr)` 后 480px 宽也不溢出，标题逐级出现省略号。
   `.col` 上的 `min-width: 0` 与 `.box` 的 `overflow-x: hidden` 是同一件事的防御写法——
   后者还顺带避开「竖向滚动条一出现、内容宽度变小，把横向滚动条也激发出来」的连锁。
   （`.box` 的 `overflow-y: auto` 会按规范把另一个轴也算成 `auto`，必须显式写 `overflow-x: hidden` 才能关掉。）
11. **界面层不重写排版。** 字号与间距只有 `base.css` 里的四档字号（`--text-xs/sm/md/lg`）
   与六档间距（`--space-1..6`），不写一次性数字；一行条目的排版（前置控件/图标 + 标题 + 副文案 + 尾部说明）
   用 `.item` / `.item__main` / `.item__title` / `.item__meta`，三处共用。
   以前每个列表各写一遍 flex 与省略号，于是只有一处记得带 `min-width: 0`，那一处的省略号能生效、其余不能。

## 十、工具链取舍

命令速查在 `AGENTS.md`（它每次都会被读），这里只记「为什么这么选」。

**`pnpm watch` 是自己的脚本（`tools/watch.mjs`），只调 `extension build`**，因此产物的权限与生产完全一致。
没有用它自带的 `extension dev --no-browser`，因为两条路都不通（2026-10-02 实测）：

- `extension build` **没有 `--watch`**，真正的监视能力只存在于 `dev` 里。
- `extension dev --no-browser` 确实能只监视不启动浏览器（日志显示 `Chrome (no-browser mode)`），
  但它**必然产出开发版清单**——多出 `scripting` 与 `management` 两个权限并写入 CSP，
  `pnpm verify` 会失败；`--no-reload` 也去不掉这两个权限。

所以监视能力由 `fs.watch` 补（`tools/watch.mjs`，去抖 150ms），而不是换构建器。

**`extension dev` / `start` / `preview` 没有做成脚本**（同为 2026-10-02 决定）：它们都要求先下载独立的
Chrome for Testing（约 150 MB，`pnpm exec extension install chrome`），换来的是浏览器自动加载与热重载；
本项目不做自动化验收，于是换成「`pnpm watch` + 手动点卡片刷新」，省掉一个重依赖。

需要时仍可临时跑 `pnpm exec extension dev`，但要先知道两件事：

1. **它不启动你系统里的 Chrome**，只用托管缓存里的 Chrome for Testing。没装时浏览器起不来，
   而 dev server 会照常打印「ready」并继续挂着——只看这一行容易误判成功。
2. **它会把 `dist/chrome` 覆盖成开发版产物**：清单里多出 `scripting` 与 `management` 权限，
   并写入 `extension-js-control.json`。此时 `pnpm verify` 必然报「权限与预期不一致」。
   所以 **`dev` 之后要再跑一次 `pnpm build`**，才能拿到可自检、可对外分发的干净产物。

**为什么这套取舍值得守**：`pnpm verify` 是本项目唯一能自动拦住「权限悄悄变多」的关卡，
而权限最小化是第 1 条约束（见 `AGENTS.md`）。任何让 `verify` 常态化失败的开发流程，
都会把这个关卡变成「反正它总是红的」——那就等于没有。
