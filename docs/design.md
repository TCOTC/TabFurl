# TabFurl 需求与初步方案

> 状态：骨架阶段。本文是需求范围与数据模型的唯一来源，代码与之冲突时以本文为准；要改范围先改本文。

---

## 一、背景

浏览器自带的收藏夹有三个做不到的地方：

1. **不能把「当前窗口」整套存下来。** 它只能逐个页面手动收藏，标签分组的名字与结构全部丢失，事后无法还原成原来的窗口。
2. **不能同时打开多个收藏文件夹。** 只能在书签管理器里一次次点进去，想并排对比两个分类做不到。
3. **不能把两层收藏夹并排摆着搬东西。** 管理器是「左边一棵树 + 右边一层内容」：左树一次只能展开一套，
   右栏只显示一层。想把条目从 A 层搬到 B 层，得在树里一路展开、再瞄准那一行，
   而「另一层里现在还剩几条没搬」这件事从头到尾看不见。

TabFurl 只补这三块。它**不做**通用收藏管理：新增标签、笔记、全文检索、失效链接检测都不在本项目范围内，这些交给浏览器自带的收藏夹（以及用户已有的同步、导入导出能力）。

> **边界说明（2026-10-03 扩过一次）**：第 3 条把范围从「窗口 ⇄ 收藏夹」扩到了「收藏夹 ⇄ 收藏夹」。
> 扩的理由就是上面那句：它不是「再做一个书签管理器」（那件事浏览器做得更好，我们连阅读页都因此删掉了），
> 而是把**搬运**这一个动作做成看得见的——两栏各自停在一层，条目在两栏之间拖就是 `bookmarks.move`，
> 剩下多少、搬去了哪儿全程在屏幕上。仍然不做的东西见下面的非目标。

## 二、目标与非目标

### 目标

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| F1 | 窗口 → 书签（可选范围） | 把当前窗口的标签按标签分组存进**右栏当前展示的那一层**（或其下的某个子文件夹）。保存前可以逐枚勾选要保留哪些标签，整组也可以一键勾掉；也能只把**一条**标签或**一个**分组拖过去 |
| F2 | 书签 → 窗口（可选范围） | 打开当前展示的那一层里的分组与散装书签，按它的**子文件夹（一层）**创建对应的标签分组；也可以逐枚勾掉不想打开的标签，或用「打开不建分组」不要分组 |
| F3 | 打开书签管理器 | 把当前展示的那一层交给浏览器自带的书签管理器（`chrome://bookmarks/?id=<层>`），在那儿看全貌、批量整理 |
| F4 | 收藏夹管理 | 在当前展示的那一层里新建文件夹、重命名、删除（两步确认），并逐层浏览 |
| F5 | 撤销 | 撤销最近一次保存（删除那一次新建的书签与分组文件夹） |
| F6 | 零网络 | 不申请任何 `host_permissions`，不发任何外部请求 |
| F7 | 收藏夹 ⇄ 收藏夹 | 左栏可以切成收藏夹视图——两栏各自停在一层（都能导航、能就地展开、能改名删除），条目在两栏之间拖就是 `bookmarks.move`（**移动**，不是复制）。两栏共用同一份「收藏文件夹」列表，但「我站在哪一层」各管各的 |

### 非目标

- 标签、笔记、多维归类（那是另一个产品）
- **批量整理工具**（合并、去重、失效链接检测、全文检索）：F7 只是在书签树里搬条目，
  读写的仍然只有那棵树，不引入第二份数据
- 双向实时同步（三方状态冲突的成本远高于收益）
- 与思源等外部笔记软件的集成
- 自建存储：**书签树是唯一存储**，不引入 IndexedDB

## 三、书签树数据模型

```
📁 标签页存档                    ← 一个普通的书签文件夹（不是扩展建的），也是收藏的一层
   ├── 📁 工作                    ← 标签分组（分组标题原文），多次保存会累加进来
   │      ├── 🔖 标题 A
   │      └── 🔖 标题 B
   ├── 🔖 标题 C                  ← 窗口里没进分组的标签，就地放成散装书签
   └── 📁 阅读
```

**没有「会话」这一层。** 每次保存都是往**右栏当前展示的那一层**里**追加**，
不像早期版本那样每次保存先建一个带时间戳的会话文件夹。层级最多两层（分组 → 书签），
把窗口里的每个分组直接写成当前层的子文件夹。三条结构规则：

- **写入目标是右栏当前展示的那一层，而「从哪一层开始」由收藏文件夹决定。** 扩展不建文件夹、不往「其他书签」里写任何东西。
  **收藏的候选只来自书签栏**（`getBookmarksBarId()` 认 id `1`，认不出就报错），**绝不退化为「其他书签」**——
  位置只能来自用户的明确指定，扩展不替用户决定往哪里写；也不提供「自动创建文件夹」这类动作。
  **chip 栏挂在右栏表头下面一行**（右栏的起点就由它决定），而不是页面顶栏：放到顶栏上离它要影响的那一栏太远。
  chip 栏本身不依赖任何面板，所以由 `App.ts` 挂进 `TransferPanel` 留出的那一行——面板只提供位置。
  **顺序有意义**：数组里第一个**可用**的就是打开界面时的落点，所以 chip 支持拖拽排序。
  **两个加收藏的入口走同一个 `add()`**：☆（拿右栏当前层）与 ＋（打开可搜索的选择器，从书签栏里挑）。
  同一件事两个入口，各写一份去重与落盘逻辑就会分叉。
  **三种拒绝原因说三句不同的话**（书签树的根 / 不在书签栏 / 这一层没了）：它们看起来都像「按了没反应」，
  把根也归到「不往其他书签里写」就会给出错误的解释。
  **一个收藏都不可用时退回书签栏**（那是面板的事，不是 chip 栏去改面板的落点）：
  收藏里可能已经删掉了几个，所以要逐个试到第一个读得出路径的；一个都没有时落到书签栏——
  那是唯一一个“总是有意义”的层。
- **直接子级严格按窗口顺序排列。** 标签分组建成了子文件夹，窗口里没进分组的标签建成散装书签，**插在它们原来的位置上**——不会被集中挪到末尾，也不会有「未分组」这一层。窗口里一个分组都没有时，结果就是一列散装书签，所以「保存 → 还原」始终是对称的。
- **同名文件夹允许共存。** 书签树本来就允许同级同名（浏览器自己的收藏夹也允许），而且用户在不同窗口里可能真的有两个叫「工作」的分组，所以**不合并、也不追加 ` (2)` 序号**。
  代价是存档里可能出现多个同名文件夹，靠位置区分。

### 这样做的代价（三条已失去的能力）

没有会话层之后，下面三件事**永久消失**，不是待办：

1. **快照隔离**：存两次到同一个文件夹，两次的标签混在一起，再也分不出哪几条是这一次存进去的。
2. **按时间排序**：分组文件夹的名字是用户自己的分组名，没有时间戳；列表顺序就是书签树顺序。
3. **跨会话的撤销**：没有「刚建的那棵子树」可删，撤销只能是「删掉这一次新建的书签与分组文件夹」，
   所以它靠内存里记下写入时新建的 id 来实现（见 `SaveResult`）。**关掉界面就失效**——
   早期版本把会话 id 存进设置，那样重启后还能撤销；现在没有那个字段了。

取舍的出发点：把存档当「标签页池子」用（不断往里扔，需要时整包还原成窗口），而不是当「历史快照」用。

## 四、命名规则

命名只在 `src/shared/naming.ts` 里实现，界面层不得自己拼字符串。

| 层级 | 规则 | 示例 |
| --- | --- | --- |
| 收藏的文件夹 | **不由扩展命名**：用户在书签栏里指定已有文件夹 | `标签页存档` |
| 分组 | 分组标题原文 | `工作` |
| 空标题分组 | `未命名分组（蓝）`，用颜色消歧 | `未命名分组（蓝）` |
| 手动新建的文件夹 | 默认**本地时间戳**（`formatTimestamp()`）；同理同名共存，只避开「同一层里完全同名的默认名」 | `2026-10-03 13:47` |

新建的文件夹建在**右栏当前展示的那一层**，不是某个固定的起点。
时间戳做默认名是因为按「新建文件夹」的人多数只是想要一个「先放一下」的容器，
而手打的名字想不出来——回车就能建；想改名的人接着在最前面打自己的名字即可（光标会放在最前面）。
只在同一分钟内连建两个才会撞名，那时追加序号，这不是去重机制。

> 上表就是**写进书签的实际形态**：`sanitizeFolderName` 只做控制字符、空白与长度这三件事，
> 不动任何可打印字符（见下面的清洗规则）。

**没有会话命名这回事。** 早期版本会给每次保存产生一个 `名字 · 2026-10-02 14:30` 的会话文件夹，
于是命名层要千与时间戳拼名字、按预算截断、重名去重。取消会话层之后这些全部消失：

- **没有会话时间戳**：分组文件夹的名字是用户自己的分组名，不需要排序保险。（新建文件夹的默认名
  确实也是时间戳，但那是「新建后还没起名」的占位，与「每次保存都包一层时间戳」是两回事。）
- **没有自定义会话名**：输入框、预览行与 `formatSessionName` 一起删了。
  顺带记一下那个本来就不可能的需求：「窗口自定义命名」——`chrome.windows.Window` 根本没有
  `title` / `name` 字段，Chrome 也不提供这个功能。
- **没有去重**（`dedupeName` 已删）：同名允许共存，见第三章。

**清洗规则**（`sanitizeFolderName`）：

1. 去掉控制字符（`\u0000-\u001f`、`\u007f`）
2. 折叠连续空白为一个空格，并去掉首尾空白
3. 截断到 100 字（截断处再去尾随空白）

**可打印字符一律保留原文**，包括 `/ \ : * ? " < > |`。Chrome 不禁这些字符（`create()` 的
`title` 就是个普通字符串，官方文档没写任何禁用字符或长度上限），所以不做替换。
早期版本会把它们换成 `_`，那是为「导出为文件路径」提前挡 Windows 的非法字符；
**那个功能没有做，规则随之删掉**（依据：不为没实现的功能付出改名的代价）。
真要做导出时再补，届时还得处理 Windows 的保留设备名（`CON`、`NUL`、`COM1`……）与不能以点结尾两条。

## 五、还原规则

| 输入 | 行为 |
| --- | --- |
| 子文件夹 | 建一个同名标签分组（关掉「建分组」时跳过这一步） |
| 子文件夹里的书签 | 打开标签并归入该分组 |
| 当前层顶层的散装书签 | 打开成**未分组**的标签，位置按它们在文件夹里的次序 |
| 被勾掉的书签 | 不打开；因为它而空掉的分组也不创建 |
| 子文件夹里的**子文件夹** | **跳过**（只处理一层），数量计入 `skipped` 并在界面显示 |
| 浏览器内部页面 | 跳过，计入 `skipped` |
| 分隔线（占位书签） | 跳过，不为它打开标签；**不计入 `skipped`**（它不是「丢了东西」） |

因为恢复时是**按当前层的子级顺序**依次开标签的，还原出来的标签次序与保存时一致：未分组的标签会回到它们原来的位置，而不是被堆到末尾。

#### 两种组织记号：分隔线与间隔

Chrome 早已不支持书签分隔线，社区的做法是收藏一个**指向固定网址的书签**来模拟
（`https://separator.mayastudios.com/index.php`，判定见 `urls.ts` 的 `separatorKind()`）。
同一个网址靠 `?t=` 参数分成两种形态，它们在书签栏里的用途、名字与外观**都不一样**：

| 名字 | 网址 | 外观 | 为谁准备的 |
| --- | --- | --- | --- |
| **分隔线** | `index.php`（无参数） | 一枚竖线图标 | **横排**——书签栏那一排要一条竖线才隔得开 |
| **间隔** | `index.php?t=horz` | 一条通栏横线 | **竖排**——书签列表要一条横线才隔得开 |

**名字与外观必须成对**，这是刻意设计而不是随便取的：新建它们的是两个只差一个字的按钮，
要是都画成一条线，用户既分不清自己刚建的是哪一个，也看不出它们在书签栏里各管什么。
实测数据里 306 枚是 `?t=horz`（间隔）、只有 4 枚是无参数（分隔线）——
后者在书签栏里就是四根竖排用的竖线，与它们旁边的横线不是一样东西。

TabFurl 把它们当成书签树里的组织记号，而不是页面：

- **右栏按名称与外观分开画**：分隔线画一枚竖线（占一个与网站图标**等宽**的槽位，
  所以它落在同一列的中心上）；间隔画一条横线，横跨整行，条目标题非空时嵌在线的正中（「—— 标题 ——」）。
  标题**首尾的 `─` 会被剥掉**（`separatorTitle()`）：很多工具把标题写成 `──── 工作 ────`，那两道横杠是手画的线，
  而我们已经用 CSS 画了线，留着就成了第二条——长度写死、跟容器宽度对不上。剥的时候把**空白当成同一类字符一起剥**，
  所以 `─ ─ ─` 这种用横杠加空格拼出来的假线会整条消失，退化成只有一根线的形态（正是想要的）。只动首尾：
  `2020 ─ 2024` 中间那根是标题的一部分。
  真实数据里 17 种标题都是「教程────────────」这种**尾随**横杠，剥完得到 `教程`；
  判定与清洗对全部 310 枚**零误伤、零漏网**。
- **行内有一个「转成另一种」**（`data-swap-separator`）：它就是 `updateNode(id, {url: 新网址})`，
  **只改网址、不动标题**——标题是用户写的，与横竖无关。两种形态的网址由
  `separatorUrlOf()` / `toggledSeparatorKind()` 一对函数保证可往返（测试里循环验证了这一点）。
- **它保留原位**：渲染一层时，文件夹、书签与两种记号按书签树顺序依次排下去，
  **不要拆成「先文件夹、再散装书签」两段**——一拆，用户放在中间的记号就全被推到列表末尾，
  而用户放它们就是为了把相邻的几组隔开，位置一丢，记号就只剩装饰作用。
- **它不算书签**：`FolderOption` 的两个计数、右栏的「打开（N）」与文件夹副文案都不含它；
  它也没有勾选框（勾选维度是「要打开哪些标签」，它不是其中之一）。
  书签树那一侧的判据是 `isRealBookmark()` / `realBookmarks()`（`shared/bookmarks.ts`），
  **不能用「有没有 url」代替**：渲染要画记号、计数要跳过它，用同一个写法就只能对一头。
  漏一处的症状：右栏「打开（N）」多算，而且全选框按这份名单算总数，会被永远勾不上的项拖在「部分选择」上，
  点了全选也回不到「全不选」。
- **不参与还原**，也就不会多出一个无用标签。

判定按**主机名 + 路径**，忽略协议与片段：同一个记号在不同工具、不同时期会写成 `http` / `https`。
只认该域名下的 `/index.php`（以及省略路径后被浏览器补成 `/` 的写法）——不能只认主机名，
那会把该域名下的任意页面也当成记号。`?t=` 只把 `horz` / `horizontal` 认作横向，其余
（无参数、`?t=vert`、其他参数）一律算竖向——竖向本来就是默认形态。

实现在 `src/app/TransferPanel.ts` 的 `archiveBookmarkRow()`（分出 `.marker--sep` / `.marker--gap`），
与 `restore.ts` 的 `PlannedBookmark.separator` 共用同一份判定：记号照常留在 `planRestore()` 的计划里，
只有真正的标签才走 `restorableBookmarks()`。只含记号的子文件夹等于空子文件夹，不产生项。

**还原去向**由按钮直接决定，不是存起来的偏好：打开标签去哪里属于「这一次要开到哪里」，
同一个存档两次可能选得不一样。所以**不要把它加回 `Settings`**。

「**建不建分组**」是另一个维度（同一份计划，只是不建分组、子文件夹的名字丢掉，即 `groupTabs: false`），
所以它用一个复选框表达，而不是再开一个按钮——否则两个按钮之间的并集关系得靠用户自己推。
而「不建分组」本来就可以用在当前窗口与新窗口两种情况上。
复选框的文案是「**打开**不建分组」：光写「不建分组」会被读成也管上面那个「存过去」。

| 入口 | 去哪 | 建不建分组 |
| --- | --- | --- |
| `← 打开` | **当前窗口** | 看「打开不建分组」复选框 |
| `＋ 新窗口` | 新窗口 | 看「打开不建分组」复选框 |

它打开的是**右栏当前展示的那一层**（`viewFolderId`），不是无条件打开第一个收藏文件夹。
新窗口通过第一个标签顺手创建，避免先开空窗口再补标签的闪烁。

`← 打开` 走当前窗口而不是新窗口：它与 `＋ 新窗口` 是同一件事的轻重两档，
而「打开」这个动作在多数时候是「接着现在这个窗口用」。把几十个标签塞进当前窗口是不可撤销的，
所以另一档（新窗口）必须有一个同样显眼的按钮，而不是藏在别处。

**打开的标签默认不加载**（懒加载）。

`chrome.tabs.create()` **没有**「先不加载」这个选项——传了 `url` 就会立即开始加载，
`active: false` 只是不聚焦，所以一次还原几十个标签会造成瞬时并发加载而卡顿。
真正能做这件事的是 `chrome.tabs.discard()`（Chrome 54+）：从内存卸载，但标签仍在标签栏上
（标题、位置、标签分组都保留），点开时才重新加载。

三条实现要点：

1. **舍弃必须放在建分组之后**。分组、窗口都完成了，标签的位置与归属已固定，此时卸载最安全。
2. **活动标签无法被舍弃**（API 限制：`tabs.discard` 对活动标签不生效），所以每个窗口会留一枚已加载的。
   这正好让人看得见窗口确实开出来了。
3. **舍弃失败不能拖垮整次还原**：标签已经打开了，只是会真加载而已，所以逐个 `try/catch` 只记日志。

#### 必须先等导航提交，否则标签会变成 about:blank

**这是实测到的 bug（2026-10-03），不是理论风险。** `discard` 的语义是「卸载已加载的内容，
激活时按记录的地址重新加载」；如果标签还在加载、没有任何**已提交**的地址，Chrome 就没有可恢复的地址，
标签会落到 `about:blank`。

判定依据就在 `Tab` 的文档里：`Tab.url` 是「主框架的**上次已提交**网址……**如果标签页尚未提交，
则可能为空字符串**」，而目标地址只出现在 `Tab.pendingUrl` 里。所以「刚 `create()` 完就 `discard`」
必然丢掉地址——`create()` 返回时导航还在路上。

因此现在轮询到 `Tab.url` 有值（且 `pendingUrl` 已清空）才动手：

- 每 50ms 查一次，最多等 2 秒。整体是**同步等待**的，所以超时上限直接决定状态栏会卡多久。
- **超时就干脆不碰那枚标签**，让它照常加载。即「宁可少省点内存，也不能把标签弄成空白页」。

代价要说清楚：等待提交意味着**每个标签仍会发起首次请求**（DNS、连接、响应头）。
省下的是最贵的那部分（渲染、JS、子资源、内存），省不掉网络往返本身。

#### 行尾的「加载 / 加载中 / 释放」：内存的取与还，都不切过去

懒加载有个代价：用户想「先把这几页读出来」时，只能一个个点过去，而点过去就换页了。
反过来也有代价：几十枚页面同时驻留内存时，「这几个我还想看、其余先放掉」办不到。
所以左栏行尾那一个位置承担两个方向的动作，都**不改变 `active`**（不切走手上这一页）：

- 「加载」只做 `chrome.tabs.reload()`：对卸载掉的标签，重载就是「加载」——内容被丢掉、地址还记着。
- 「释放」只做 `chrome.tabs.discard()`：丢掉内容、保留标题与地址，点开时才重新加载。

`reload` 这条路径是 Chrome 自己的 API 测试覆盖过的
（`chrome/test/data/extensions/api_test/tabs/basics/discarded/discarded.js`：先断言标签已卸载，
再 `chrome.tabs.reload(id)`，然后在 `onUpdated` 里断言 `changeInfo.discarded` 为 **false**）。

判据是 `Tab.status`，一共三档：

| 状态 | 行尾 | 说明 |
| --- | --- | --- |
| `unloaded` | 「加载」（可点） | 内容被 Chrome 丢掉了（懒加载出来的，或它自己卸的） |
| `loading` | 「加载中」（禁用） | 点过「加载」之后、到页面给出标题之前 |
| `complete` 且非活动 | 「释放」（可点） | 已经把这一页读进内存了 |
| `complete` 且**活动** | 什么都不占 | 它就在屏幕上，卸载它没有意义 |

用 `status` 而不是 `Tab.discarded`：两者在「卸载」这一档**等价**（Chrome 自己的 API 测试断言
卸载时 `status === 'unloaded'`），但 `status` 能把「正在加载」也表达出来，而界面恰好需要那一档。

#### 为什么活动标签不给「释放」

**这不是 API 拒绝，是我们自己的选择**，而且理由很具体：活动标签就在屏幕上，
卸载一个看得见的页面没有意义——浏览器马上就会把它读回来。

来源核查（因为它反直觉）：`tabs.discard` 用的理由是 `EXTERNAL`，而
`DiscardEligibilityPolicyTest.TestCannotDiscardActiveTab` 明确写着只有 `URGENT` / `PROACTIVE` /
`SUGGESTED` 受保护，`EXTERNAL` 对活动标签**是允许的**（扩展就是 EXTERNAL 这条路）。
所以判据得自己给：Chromium 自己的 discards 页用的是 `visibility !== VISIBLE`（`canDiscardViaUi_`），
扩展能看到的最接近的信号就是 `Tab.active`。

因此 `Tab.active` **也必须进 `windowSignatureOf()`**：它不显示在行里，但决定给不给那个按钮，
漏掉就会出现「该重画的没重画」——把标签切走之后那一行还挂着「释放」。
`tabs.onActivated` 同样要触发刷新（去抖过的一次 `tabs.query`，不值得为此记住「我们的窗口 id 是几」）。

#### 释放可能换掉 tab id：勾选必须搬过去

**这是本轮最容易静默出错的一条。** 扩展看到的 `Tab.id` 是
`SessionTabHelper::IdForTab(webContents).id()`（`extension_tab_util.cc`），
而释放的旧实现会把 WebContents **换成一个新的**（`TabLifecycleUnit::FinishDiscard` →
`tab_strip_model_->DiscardWebContents`），新的那个有自己的 SessionTabHelper → **新的 tab id**。
Chrome 自己的 API 测试里就写着这件事（`discarded.js`：「the id changes after a tab is discarded」）；
`TabListInterfaceObserver::OnWebContentsReplaced` 的注释也点明了这条路径的存在
（「used on Desktop to maintain backwards compatibility with the old discard path」）。
新的 `kWebContentsDiscard` 路径会保留 WebContents（`FinishDiscardAndPreserveWebContents`），
所以这个行为**取决于一个 feature flag**，扩展不能假设 id 稳定。

而界面里「勾选了哪几枚」正是按 tabId 存的，`refreshWindowOnly()` 又会把「不在窗口里」的 id 剪掉 ——
于是不处理的话，勾选会在释放的那一刻**静默丢掉**（实测把一枚勾上的标签移出窗口，计数从 1 变 0）。

`tabs.onReplaced(addedTabId, removedTabId)` 给的正好是这张新旧对照表，所以迁移就是一行：

```ts
if (windowSelected.delete(removedTabId)) windowSelected.add(addedTabId)
```

**迁移必须在刷新之前**：`scheduleWindowRefresh()` 是去抖的，但一旦跑起来就会剪掉那个已经不在窗口里的旧 id。
实测（预览桩模拟一次换 id）：勾选从 `1` 变成 `903`，「存过去 (1)」纹丝不动。

其余四条实现要点：

1. **`tabs.onUpdated` 的过滤必须带上 `changeInfo.status`**。它只在卸载 / 开始 / 加载完三种时候派发
   （Chrome 把它与 `discarded` 塞在同一个事件里，两者永远同时到达），少了它点完那一行不会变。
2. **`status` 与 `active` 都必须进 `windowSignatureOf()`**。签名是用来「结构没变就跳过重建」的，
   漏一个字段的后果正是「该重画的没重画」——那一行会停在上一个样子。
3. **三档共用 `.btn--load`（定宽 `--load-btn-min`）**。「加载」两个字、「加载中」三个字，
   不定宽就会在切档时差一个字宽。它在「打开」**左边**（按钮组贴右，
   在右边的话消失时会推走「打开」；实测放左边时右边那枚纹丝不动，全程 592px）。
4. **点下去只报「已在后台加载」，不承诺标题**；释放则不写成功提示（那一行自己会变成「加载」），
   但失败要写——它是有真实拒绝条件的（已是 `unloaded`、没有 WebContents、有未提交的导航在等），
   而且此时 Chrome 抛的是 `Cannot discard tab with id: N`。

#### 为什么点了「加载」标题可能不变（x.com 这类站点）

标题是**页面自己给的**，什么时候给由网站决定。重 SPA（x.com 这类）在标签不可见时往往走不到
设置标题那一步，于是标题要等用户切过去才更新——扩展这边只能把「开始加载」说出来，变不出标题来。

这在 Chrome 的模型里是清晰的：`tabs.reload()` 让 WebContents 重建并开始导航，
`Tab.status` 随即变成 `loading`，而 `title` 要等页面调用设置标题（`TitleWasSet`）才会有。
**所以「加载中」这一档不是装饰**：没有它，用户看到的只是「按钮消失了、标题没变」，
那看起来就是「点了没反应」；有了它，界面说的是实话「它还在加载，还没给出标题」。

实测（预览桩）：点「加载」→ 行尾变成「加载中」（禁用、同宽 52px），「打开」的位置全程不变；
再模拟页面加载完并给出标题 → 行内标题立刻更新为新的。也就是说**通知这条路是通的**，
剩下那一段（页面何时给出标题）不在扩展能决定的范围内。

状态由 `snapshotCurrentWindow()` 采集（`Tab.status`，缺字段按 `complete` 处理——
类型里它是可选的，缺了当成「已加载」才不会让每一行都冒出「加载」）；
`reload` 与 `discard` 一样不进 `Settings`、也不落盘——它是一次动作，不是一种偏好。

**反馈只在需要时出现**：「正在打开…」留在进行中（必须留：舍弃前要等导航提交，最长 2 秒，
没有它界面看起来就是卡住的）；失败时给出错误；**成功后不留报账式提示**（标签/窗口已经打开，
看得见；要打开多少在点之前就写在按钮上了）。

**勾选与计数共用一条通路。** 界面渲染的清单与还原用的计划都是 `restore.ts` 的 `planRestore()`，
界面再把勾掉的书签 id 交给 `applyExclusions()`；所以「看到几枚就会开几枚」不靠人工对齐，而是同一份数据。

## 六、平台与权限

**目标浏览器只有 Chrome**（最低 114，写在 `minimum_chrome_version`）。不做 Firefox 兼容。

这带来了实质简化，不是单纯的偷懒：

- `chrome.tabGroups`（89+）可以直接调用，**不需要特征检测与降级分支**。
- MV3 下 `chrome.*` 原生返回 Promise，**不需要 `webextension-polyfill`**，也不需要维护 `browser.*` / `chrome.*` 两套类型。
- 清单是纯 MV3，**没有任何 browser-prefixed 字段**，减小了一半（含 `browser_action` / `sidebar_action` 的 MV2 形态）。

| 权限 | 用途 |
| --- | --- |
| `bookmarks` | 读写书签树 |
| `tabs` | 读取标签标题 / URL / 分组，创建标签 |
| `tabGroups` | 读取分组标题与颜色、创建分组 |
| `storage` | 保存设置 |
| `favicon` | 用 `_favicon` 端点取网站图标；**读 Chrome 本地缓存，不发网络请求**。已申请 `tabs`，所以它不额外产生权限警告（官方文档明确：只有尚未申请 `tabs` 或主机权限时它才警告） |
| `host_permissions` | **无** |

图标就一张真图标（26px，与文件夹方块同尺寸），没有底色或首字母。`_favicon` 的实测行为（2026-10-02 在真实 Chrome 里验证）：
**它从不失败**——缓存里有就返回真图标，没有就返回**默认地球**，连根本不存在的域名也返回 32×32 的图片
（`onerror` 不触发）。所以代码里不需要失败处理：产物要么是真图标、要么是地球，不会出破图。
代价要说清楚：**没有图标的站点会长成一个样**，一排全是地球。
不请求 Google 的 favicon 服务，也不把 `tabs.Tab.favIconUrl` 拿来渲染——后者指向网站服务器，
渲染时等于向该站点发请求。

> 如果将来要支持 Edge / Brave 等 Chromium 内核浏览器：不用改代码，直接加载 `dist/chrome/` 即可（它们共用同一套 API）。只有要支持 Firefox 才需要重做上面这几层。

依赖方向单向：`pages/` → `src/app/` → `src/shared/`。**`shared/` 不得 import 任何界面模块**。
收藏文件夹 chip 栏不是面板：它不读 `AppEvents`，而是**触发** `folderChosen` / `favoritesChanged`（增删排序即落盘）。
它由 `App.ts` 挂进两栏表头用 `FAVORITE_HOST_ID` / `LEFT_FAVORITE_HOST_ID` 标出的那两个位置——
面板只提供位置、不知道挂进来的会是什么，两边仍然互不 import。
**状态与视图是分开的**：`createFavoriteStore` 是唯一那份状态（哪几层、什么顺序），
`createFavoriteBar` 是可实例化的视图（两栏各一个）。两边各存一份状态的话，
在一条上排序、另一条不动，两块视图就开始说不同的话——而它们说的本来就是同一件事。
各自不同的只有「我这一栏正站在哪」，所以 `App.ts` 把两个取值函数分别递进去（那是**查询**不是事件）；
反方向（点 chip 要跳转）仍走 `folderChosen`，因为导航归面板所有——
带上 `side`，因为同一个「跳到这一层」的意图在两栏里的落点不一样。

**搬运的口径**（F7）：搬的单位**由行上那个勾选框的三态决定**，而三态本来就是看得见的，
所以这里不需要再引入一个选项，用户也不用学第二套读法：

| 勾选框 | 搬的是 |
| --- | --- |
| 文件夹**整选** | 那个文件夹本身（`bookmarks.move` 会连整棵子树一起带走） |
| 文件夹**部分 / 全不选** | 里面勾上的那几枚书签（文件夹留在原地） |
| 一枚书签 | 那一枚 |

于是「取消勾选其中几枚」这件事本身就改变了搬的单位：想整搬就整选，想挑几条就把不要的去掉。
**而拖拽那条路不按三态走**——拖哪一行就搬哪一行（拖文件夹行搬的是它自己），
因为拖指的是「这一个具体的东西、放到那个具体位置」，按钮说的是「把勾选的搬过去」。
两者本来就不是一个问题，所以两条路的口径不同是应该的。

「移动过去 (N)」的 N 是**要被搬走的条目数**（整选的文件夹算一条），
与旁边「打开 (N)」按书签数**刻意不同**：打开出来的是一枚枚标签，搬走的是一个文件夹。
具体搬什么写在按钮的悬停提示里（「1 个文件夹与 3 枚书签」）。

三种情况会留在原地，而且都要说出来——不说的话用户看到的是「点了没反应」：
① 本来就在目标那一层的（两栏停在同一层是最常见的状态：都是打开界面时的起点）；
② 要被搬进它自己里面的文件夹（另一栏完全可以导航进去）；③ 一条都搬不动时整件事直接说不做。
第 ① 条要跳过而不是照搬：`bookmarks.move` 对「搬到同一个父级」的行为是**追加到末尾**，
而用户要的显然不是「把这几条排到最后」。**拖拽那条路不跳**：同层重排正是它的正当用法。

左栏那份数据**只在自己可见时才读**：窗口档下它是 `display: none`，读了也白读（还多一次 `getSubTree`）。
切档时左栏记得自己上一次停在哪一层；只有第一次才落在第一个可用收藏上（与右栏同一个起点）。

界面只有一个页面：

- `pages/app.html` —— 主界面，点工具栏图标以**独立标签页**打开。
  **以窗口为单位**：同一个窗口里已经开着就切过去（不重复开），点别的窗口的图标则在那一个窗口里开。
  主界面左栏列的是「这个窗口」的标签页，所以点哪一窗就该出现在哪一窗；
  早先做成「全局唯一实例」时，在窗口 B 点图标会跳到窗口 A，等于把用户拽走。
  **页面里没有标题块**（在标签页标题上，见 §七），直接是等宽的两栏与中间一条窄操作列：
  - **左：当前窗口（可以切成收藏夹）** —— 表头那枚两档控件决定这一栏装什么（F7）。
    装标签时：按窗口顺序列出标签（分组是带缩进的块，未分组的标签就地在原位），逐枚勾选要保留哪些。**默认一条都不选**（理由见下）。
    每行末尾是一个居右的「打开」：这一栏是**活着的**标签的清单，对着它点一条就是要跳到那一条上去，
    所以它是 `tabs.update({active: true})` 而**不是**再开一个。跨窗口时还要 `windows.update({focused: true})`，
    否则主界面与它在不同窗口时看着就是「点了没反应」。
    全选框那一行的**右端**还有一个刷新按钮（见 §八 18）：标签变化本来就会自动重读，
    它只是留给「界面看着不对」时的一手。  - **中：两个方向** —— 一个「存过去」，两个打开入口：`← 打开`（当前窗口）、`＋ 新窗口`，
    各自带当前勾选的数量；下面一个**「打开不建分组」复选框**（作用于那两个打开按钮）。
    「存过去」与它们之间多留一道间隔：那是两个相反的方向，等距排下来会被看成一个整体。
    按钮等宽（`align-items: stretch` + grid 的 `auto` 轨道），宽度下限靠 `--move-btn-min`（96px）——
    光靠 max-content 不行：文案里带着计数，位数一变 max-content 就变，整列就跟着抖动。
  - **右：收藏夹** —— **一个可导航的浏览器 + 就地展开**：双击子文件夹（或点「进入」）进去，**退路就是面包屑**
    （当前层之外都能点，包括某个收藏**之上**的那几层）；**点行首那枚方块把子级就地推开**（不换页，
    也不改写入目标），方块平时是文件夹图标、悬停 / 聚焦 / 已展开时换成折叠三角。
    **没有「上一层」按钮**：一样东西两个入口，总有一个会先被人遗忘。
    表头下面一行是**收藏文件夹**的 chip 栏：chip 点一下跳过去、× 取消收藏、chip 之间可拖拽排序；
    右边两个**只有图标的按钮**——☆ 收藏当前层，＋ 打开可搜索的选择器（见 §三）。
    当前的这一层就是**写入目标**（「存过去」「新建文件夹」「＋ 分隔线」「＋ 间隔」「拖到空白处」都落在它里面）。
    全选框那一行的**右端**也是一个刷新按钮（与左栏对称，见 §八 18）。
    子文件夹行带三态勾选框（=「它里面那一层书签」）、改名、删除（两步确认）。**默认全不勾**。

行内操作分三种：**书签行**是「打开 / 修改 / 删除」，**文件夹行**是「进入 / 改名 / 删除」，
**两种记号**是「转成另一种 / 修改 / 删除」，删除一律两步确认。
三套共用同一组处理器与同一份状态——改名与删除对书签、文件夹、记号本来就是同一件事，
各写一份只会让「两步确认」的行为分叉。四个细节不能删：

- **书签的「修改」走模态弹窗**（`BookmarkDialog.ts`），因为它有标题**与网址**两个字段，行内一个输入框放不下。
  用原生 `<dialog>` + `showModal()`：Esc 关闭、焦点回到触发点、背景惰化、`::backdrop` 都是白送的。
  单例复用（已打开时先 `close()` 再 `showModal()`）——否则连点两下会报 `InvalidStateError`。
  文件夹与两种记号只有标题，继续行内改名（建完就能直接打字，不用多一次弹窗）。
  标题可以留空（记号就是这样），网址不能（清了它就成了一枚点不动的书签）。
- **记号有一个「转成另一种」按钮**（`data-swap-separator`）：它就是 `updateNode(id, {url: 新网址})`，
  只改网址、**不动标题**（标题是用户写的，与横竖无关）。两种形态的网址由
  `separatorUrlOf()` / `toggledSeparatorKind()` 这一对函数保证可往返，测试里循环验证过这件事。
- **点「打开」先挡内部页面**（`isInternalUrl()`）：Chrome 不允许扩展打开 `chrome://` 之类，
  不挡的话用户看到的是 API 抛的原始错误，而这类书签真实存在于用户的收藏夹里（实测 `chrome://discards/`）。
- **改名时不显示「回车保存，Esc 取消」**：默认的 Enter / Esc 行为本来就符合预期，不用占半行去解释。

**文件夹行的副文案是「N 个书签 • N 个文件夹」，两个数字都只算直属子级。** 这是个语义选择，
不是性能妥协——**保持直属是为了能一眼判断「能直接打开的标签页有几枚」**：

| 这一行上的数字 | 口径 |
| --- | --- |
| 副文案「N 个书签」 | 直属真书签（不含记号、不含子文件夹里的） |
| 副文案「N 个文件夹」 | 直属子文件夹 |
| 勾选框 | 只勾这一层的书签 |
| 「打开（N）」 | 只算这一层（`restoreFolder` 只处理一层） |

四个数字同一口径，才对得上：勾上那一行、点「打开」，开出来的枚数就是副文案里那个 N。
如果改成递归到后代，「专题研究」那行会显示 312，而它旁边的勾选框只能勾 18 条——
反而让人以为勾上就会开 312 个。

递归计数**不要钱**，所以别拿性能当理由把它改回去：`refresh()` 读的是 `getSubTree(viewFolderId)`，
它本来就把整棵子树读进了内存，递归只是纯内存遍历。实测真实数据（10205 枚书签 / 798 个文件夹 /
最深 7 层）：整棵书签栏递归计数 **0.42ms**、根层 25 个子级各自递归 **0.38ms**，
比读一次 `getSubTree` 本身（0.57ms）还便宜。而且因为这个算法已经在生产路径上跑着
（`describeFolder()` 的 `totalBookmarkCount`，「＋ 添加收藏…」打开时会把整棵书签栏跑一遍），
它到底快不快早就被验证过了。

条目上是两行文字：标题 + **完整网址**（不是主机名）。收藏夹条目本来就靠网址区分同名页面，
而 10px 的字能把绝大多数网址在一行里装完（实测 7 条里 6 条完整，剩下那条是 424 字的 `data:` 网址，
只能省成省略号 + `title` 悬停）。两行文字的总高（24.9px）刻意卡在图标（26px）以内：
超过了会把行撑高、图标周围空出一圈，看着像没对齐。
**`.favicon` 与 `.folder-tile` 必须一样大**（都是 26px，字形 19px）：两者在同一列里交替出现，
差一像素标题左缘就错开（实测改前 22px 时文件夹方块看着比满格的网站图标小）。

右栏的列表框分两层：`div.box` 是框架与滚动容器，`ul.list` 才是逐行的列表。
「当前位置（面包屑）+ 导航按钮」放在框内的 `.box__top`，并且 `position: sticky` 贴着框顶——
两者是同一份内容的两个视角（「我在哪」与「这里有什么」），摆在一起才不用在两个区域之间来回对；
粘住是因为列表可以很长，滚到一半时退路不该消失。
**任何静态内容都必须放在 `.box__top` 里**：`renderArchive()` 每次都会重写那个 `ul`。

### 为什么「两边都是收藏夹」的入口在左栏表头

F7 是一个**模式**：左栏在「当前窗口」与「收藏夹」之间切换。入口就长在**左栏表头**
——把那个 `<h2 class="col__title">当前窗口</h2>` 换成一枚两档的分段控件（`当前窗口 | 收藏夹`）。
三条理由，前两条是「别处不行」，第三条是「这里正好」：

1. **模式改的就是左栏装什么**，入口就该长在它改变的那件东西上。放到顶栏或底部，
   用户要先建立一次「这点的是左边」的心智映射；而页面标题块已经删掉了（省的像素给了两个列表），
   再加一行顶栏是往回走。
2. **中间那一列不能放。** 那里在模式 2 下要换成另一套按钮（见下），
   把模式开关混进按钮堆里会被读成「这也是一次操作」——而它其实什么都还没做。
3. **不新增一行高度。** 左栏表头本来就在（标题 + 一枚胸章），右边一大片空着；
   右栏同一个位置放的是整条收藏 chip 栏。于是两栏表头从此对称：
   **左边是「这一栏看什么」，右边是「这一栏从哪开始」**。

模式切换的三条后果（都已定，实现时不要各自发明）：

- **两栏是同一个组件的两个实例。** 右栏那一整套（面包屑、就地展开、虚拟滚动、行内改名删除、
  勾选、拖拽落点）必须被实例化两次，**不能复制一份**——两份实现一定会分叉，
  而分叉的表现是这个项目反复要避免的那类错觉（列表看着全选、按钮说没选中）。
- **两栏共用同一份收藏列表，但「我站在哪一层」各管各的。** 在任一栏加/删/排序，
  两栏的 chip 栏一起变（`FavoriteFolders` 要从单例变成「一份状态、两块视图」）；
  点某一栏的 chip 只跳那一栏。两栏各自记自己的 `viewFolderId` / `expandedIds` / 勾选集。
- **中间那一列换档。** 书签 → 书签的「存过去」其实是 `bookmarks.move`（移动），
  而 `打开 / 新窗口 / 不建分组` 是窗口语义，在这里没有意义。所以模式 2 下中间列是
  「→ 移动过去 / ← 移动过来」，其余收起。

**切入时的落点**：左栏**第一次**切到收藏夹时，与右栏一样落在第一个可用的收藏
（没有收藏则退回书签栏）——两栏一开始内容相同是刻意的，它是最可预测的一种默认，
用户接着把其中一栏导航到自己要看的那层即可。
之后再切档**留在原地**（与右栏刷新时同一条规矩：能留在原地就留在原地），
否则「过去看一眼再回来」会把用户刚才导航到的那一层弄丢。

### 为什么右栏是「可导航的浏览器 + 就地展开」两层并存

早期版本把存档列成一棵可以「全部展开 / 全部折叠」的树，子级用缩进链表达层级。它有两个问题：

1. **深入到第三、四层时，缩进链会把面板压成一条细缝**，每一层都在抢横向空间，而收获只是「看到了下级」。
2. 根节点的子级通常是二十几个文件夹，展开后的信息量远超一屏，用户实际能做的仍然是一层一层看。

于是改成了导航器：**退路是面包屑，O(1)**，横向空间不再随深度衰减；面包屑又把「我在哪」当场告诉你。
这不是一个「更好看的树」，而是一个不同的交互模型：树在回答「整体长什么样」，导航器在回答「我现在在哪、能往哪去」。

#### 后来又加回了「就地展开」，两条理由仍然成立

导航器唯一的缺口是：想「只看一眼里面有什么」时必须来回跳——进去、看完、再退回上一层。
所以在导航器之上又加了一层 Finder 式的就地展开：**点行首那枚方块把子级推开**，不换页、不丢上下文。

两者**并存而不是互相取代**，因为它们回答两个问题：

| 手势 | 回答的问题 | 状态变化 |
| --- | --- | --- |
| 双击行 / 「进入」 | 我**现在就在这一层干活** | `viewFolderId` 跟过去（写入目标也跟过去） |
| 点行首方块 | 我只想**看一眼**里面有什么 | 只记 `expandedIds`，写入目标与计数一概不动 |

上面那两条反对「树」的理由怎么处理：

- **缩进没有回到「细缝」**：只在用户点过的那几层上展开，而且每一层只吃 12px
  （`--tree-indent`，比左栏标签清单那一道 20px 更省）。实测真实数据最深 7 层、展开 6 层共 60px 时，
  `.box` 的 `scrollWidth === clientWidth` —— **没有横向滚动条**，这条是硬底线。
- **没有回到「全部展开就卡死」**：靠**虚拟滚动**（见下），而不是靠「不给这个按钮」。
  「全部展开」是一个按钮两档（有展开的就全部收起），因为它回答的是一个真问题：
  想在一大堆文件夹里**找**东西时，一排排点开二十几个文件夹很磨人，而全部展开之后
  可以用浏览器自己的页内查找（Ctrl+F）。

#### 虚拟滚动：行是扁平的，一次只画视口里那几十行

不虚拟化时「全部展开」的代价（实测，不是估计）：11004 行、一次 `innerHTML` 产出
**114,500 个元素 / 12 MB 字符串**，同步卡 **983 ms**、随后布局 **2402 ms**。

做法三步：

1. **`flattenArchive()` 把可见行拍平成一个数组**（只走一遍树、只产出数据、不碰 DOM）。
   实测 11004 行约 20 ms ——「全部展开」本身不贵，贵的从来是渲染。
2. **`renderArchiveWindow()` 只渲染视口 ±10 行**（`ARCHIVE_OVERSCAN`），上下各一个
   `.vpad` 占位行把滚动条撑成真实长度。滚动用 `requestAnimationFrame` 合并。
3. **行高从真实元素上量**（`rowHeight()` 挂一个探针再取高度），**不写死 38px**：
   那个数由 `--row-inner` 与 `--item-pad-y` 算出来，CSS 变量一改，写死的虚拟滚动就会错位，
   而且错得很安静（滚动条长度不对、滚着滚着跳）。

实测（同一份真实数据、同一个动作）：

| | 虚拟化前 | 虚拟化后 |
| --- | --- | --- |
| 同步 | 983 ms | **7 ms** |
| 到首帧 | 约 5.2 s | **8 ms** |
| DOM 元素 | 114,500 | **320** |
| 滚动一次 | — | 12–35 ms（含两帧延迟） |

三条由此而来的**硬约束**：

- **行与行之间不能有嵌套**，缩进只能靠 `--depth` + `--tree-indent` 表达；
  也因此所有行必须等高——连「展开块上下多 4px」这种不等高的东西都不能有。
- **不能去 DOM 里数兄弟**。插入位置改读行上的 `data-sibling-index`：虚拟滚动之后
  视口外的行**根本不存在**，`archiveList.children` 或任何「扫一遍兄弟」的写法都会数出一个
  错的层内下标，然后静默插到别的地方去。
- **滚动时如果正在改名，就不重绘**：输入框会被换成新元素，而 `focusout` 处理器会把
  「元素被移除」当成「用户点开了别处」从而把改名提交掉——打字打到一半被提交是最糟的结果。

#### 勾选框只给「会被打开」的行

展开 / 全部展开之后会看到大量**比当前层深得多**的行，它们会不会被「打开」？不会：
`restoreFolder` 只处理一层（子文件夹建分组、散装书签不建分组），所以 `archiveBookmarkIds()`
只覆盖「当前层的书签 + 每个直属子文件夹里的书签」，也就是 depth ≤ 1。

于是那些更深的行如果还给勾选框，就是一句假话：**勾了却不会打开**。而全部展开会把这个谎言
放大到近万行（满屏勾着的框，而按钮写「打开 (0)」）——正是这个项目反复要避免的
「列表看着全选、按钮说没选中」那类错觉。

所以规则是 `selectableAt(depth, isFolder)`：书签 depth ≤ 1、文件夹 depth = 0 才有勾选框，
与 `archiveBookmarkIds()` **严格同一口径**。没勾选框的行用 `.marker__slot` 占位
（它与复选框实测都是 14px），否则整列会左移一格。

这也顺带说清了两件事的分工：**勾选框回答「要不要打开」，展开回答「里面有什么」**。
想看全貌、想按整棵子树打开，用「打开书签管理器」。

#### 三条与展开绑在一起的实现约束

**一、展开不改写入目标、也不改任何计数。** 一枚方块只把子级画出来。
`viewFolderId`、每一行的勾选框、「N 个书签 • N 个文件夹」、右栏全选框的分母，全都还是「当前这一层」
那一套口径（实测：展开前 25 行 / 已选 0 / 234，展开两层后 52 行、四个数字一个没变）。

**二、行不再只属于当前层。** 展开之后有些行是后代，所以：

- 所有按 id 找节点的动作（改名 / 删除 / 打开 / 转换记号 / 弹窗改书签 / 勾选框回填）都要走
  `nodeIndex`（当前层 + 所有后代，在 `applyArchive` 里重建）。原来那些只看 `archiveChildren`
  的写法在展开之后直接找不到节点——而且是**静默**找不到（点改名没反应）。
- 落到某一行的拖拽要带上它所在的层（`data-parent-id`），否则「插到子文件夹里第 2 行」
  会被当成「插到当前层第 2 行」。`archiveList.children` 也不能再当「这一层的所有行」用。
- 行内三分法要量 `.group__head`：展开的行把子级也包在同一个 `<li>` 里，量整个 `li` 的话
  「中间 = 进去」会变成「在整棵展开块的正中间才算进去」。
- `data-enter-folder` 从 `<li>` 挤到 `.group__head`：否则双击**子级**的任意一行
  都会被 `closest()` 认成「要进外层文件夹」。

**三、拖进自己或自己的子孙要真的拒收。** 这是行内展开**新造出来**的一个动作
（以前右栏一次只显示一层，落点的锚点永远是兄弟，所以不可能形成环）。
Chrome 也会拒绝它，但不能等到报错：那会在界面上留下「拖了但没动」而没有解释的痕迹。
现在的两道：`dragover` 里把 `dropEffect` 置成 `'none'`（按规范，操作是 none 时浏览器
**连 `drop` 都不会派发**）且不画提示；`moveArchiveNode` 里再兜一层，写一句
「不能把文件夹挪进它自己里面。」——绝不报「已调整收藏夹顺序」（实测踩到过：
守卫挡住了移动，但提示线照画、状态照报成功）。

展开状态在 `expandedIds` 里（一个 `Set<string>`，**不落盘**），**换层时清空**：
它只对那一层的浏览有意义，不清就会越攒越多。
但**刷新不能清**（改名 / 删除 / 拖拽后的 `refresh()`），否则用户展开的那几层会在每次改动后当场收起来。

**展开不需要读一次书签树**：`getSubTree()` 本来就是递归读整棵子树的，子级早在 `folder.children` 里，
所以 `toggleFolder()` 只是记一个 id 再重绘——**零 IPC**。

代价与取舍：

- **勾选是跟随展示层级的**。换一层就换成那一层的选择，不会把别处的勾选默默带过来。
  这是刻意的：若保持全局勾选不变，主页顶部的「已选 N / N 枚标签页」会与眼前的列表毫无关系——
  正是「列表看着全选、按钮说没选中」那类错觉。要看全貌、要按整棵子树打开，用「打开书签管理器」。
- **文件夹行的勾选框仍然保留**，含义是「它里面那一层书签全要 / 全不要」（与 `restoreFolder` 的口径一致：
  它只处理一层：子文件夹建分组、散装书签不建分组）。所以**进不进去与勾不勾它是两件事**：
  进去是「往它里面存东西 / 接着往下看」，勾上是「打开它里面的书签」。
- **导航不受收藏文件夹限制**：面包屑里**除当前层外都能点**，包括收藏**之上**的那几层。
  所以收藏只是起点，不是写入边界。
- **面包屑的可点与不可点项必须同一个盒子**：不可点的当前层也套一层 `.path__label`，
  与 `.path__link` 共用同一条内边距规则——那一段文字会随着「往下一层」从当前层变成可点的祖先，
  盒子不同就会让整排横向抽动一下（实测两者都是 30px 才稳）。
- **书签树的根是唯一不能写入的层**（`canWrite()` = 路径长度 > 1）：Chrome 不接受在根下面直接建书签，
  所以那里「存过去」「新建文件夹」「＋ 分隔线」「＋ 间隔」禁用、拖拽不收，并用一行 `#archive-note` 说明原因与退路。
  到那一层时面包屑自然没有可点的项（它上面已经没有东西了），退路是双击列表里的「书签栏」。
  同一个事实还多一条：**根的子级不能改名 / 删除**。那三个（书签栏 / 其他书签 / 移动设备书签）是
  Chrome 的固定文件夹，两个动作都会被拒绝——管理器的 `canEditNode()` 也是这么判的（根的子级一律不可编辑）。
  所以那些行**只给「进入」**：不给按钮比给了之后报错好。两个结论共用同一个判据 `atTreeRoot()`。

### 为什么是「打开书签管理器」而不是自己做一个阅读页

早期版本有一个 `pages/folder.html`（文件夹阅读页）：整页卡片网格、自己的搜索与面包屑。
它被删掉了，当前层的入口换成了浏览器自带的书签管理器（`chrome://bookmarks/?id=<层>`）。

理由是它超出了本项目的范围（§二）：它等于长期维护第二个界面，而它想解决的问题——
“看一层文件夹的全貌、批量整理”——浏览器本来就在做，而且做得更好（可搜索、可拖到任意位置、
能多选、能新建文件夹）。扩展只补浏览器不做的那两块（整窗存取与多文件夹并排打开），
把“看与整理”交回给浏览器，才是最小职责。

一个实现上的不确定：`chrome://` 能不能被扩展打开取决于 Chrome 的白名单，而这个白名单不属于扩展控制。
所以 `openInBookmarkManager()` 用 `try/catch` 包住，失败时给出一句**可操作**的提示
（告知 `Ctrl+Shift+O`），而不是把 API 的原始错误丢给用户。

**`?id=` 用的是数字 id，看起来像 bug 的那个其实不是。** 这一点很容易看错，值得写下来：

管理器的地址栏平时显示的是 UUID（`chrome://bookmarks/?id=914d6618-…`），但 `?id=` **认的就是**
`chrome.bookmarks` 给的那套数字 id：浏览器自己的书签栏右键菜单「打开书签管理器」就是这么生成 URL 的，
而 `router.ts` 里的 `findIdByLegacyId()` 专门把数字 id 映射成 UUID——**映射成功后还会改写地址栏**。
所以「看到的一直是 UUID」与「数字 id 能用」并不矛盾，而扩展 API 里根本没有 UUID 字段可拿。

这条路径确实曾经坏过，但时间窗很窄：**Chrome 154.x**（Mojo 迁移的回归，
issue [565829425](https://issues.chromium.org/issues/565829425) / 受限制的 565108351）——
传数字 id 会静默退回默认层。当时我们据此改成了「按标题搜」，并把那个「设计」写进了文档；
后来确认那是**上游 bug**：修复（commit `60fdad74c32b2caf516f316888607881a54b0d3e`，CL 8471113，
改的正是 `bookmarks/router.ts` + `util.ts`）先进了 main（156 canary / 157 beta），
又樱桃摘到 M155（CL 8488425）——**包含它的第一个稳定版是 155.0.8059.26**，
另有一个补充端到端测试的提交 `3af685fc8cf361980d66ac4a3c1a6e0947442c3c`（CL 8496589）。
所以判断「用户那台机器上会不会看到退回默认层」，看版本号就够了：**低于 155.0.8059.26 会**。

所以现在用回 `?id=`，状态行也回到一句「书签管理器已打开。」。

**教训**：「官方文档没写、但我这版不生效」不等于「这条路走不通」。当时如果先去查
issue tracker，会看到这是一条**已被 bisect 并正在修**的回归，而不是需要绕开的设计约束。
判断一个「不生效」之前，值得先分成三种：**没这功能 / 有这功能但上游坏了 / 我用错了**。 

另外，视图**在刷新时能留在原地就留在原地**（用户是在浏览收藏夹，不该因为一次刷新被弹回起点）：
只有当前层真的没了（被删掉、被挪走）才去重新选一层（顺序是第一个可用的收藏 → 书签栏）。

### 为什么不分 Tab，以及为什么是两栏

初始版本把它拆成「保存」「收藏夹」两个 Tab。两者实际上是**同一个东西的两侧**：
左侧是一个尚未落盘的会话（标签还住在浏览器里），右侧是已落盘的会话，
数据结构同形——都是有序的「分组 | 标签」序列（即 `WindowChild` 与 `planRestore()` 的产品）。

分 Tab 的真实代价不是「多一次点击」，而是**保存完看不见它落在哪**：
想确认或直接还原刚存的那一套，得先切过去。每二条是「撤销上次保存」只在保存侧出现，
而它要撤销的那一项此时正显示在另一侧。

为什么要两栏（而不是更炫的方案）：**两份清单无法共享同一列高度**。
实测过几种做法：

| 方案 | 结果 |
| --- | --- |
| 草稿置顶 + 下方存档（用 `sticky`） | **不可行**：粘性元素一旦高于滚动容器，受「容器边界」约束就钉不住，会跟着内容一起滚走 |
| 草稿/存档互斥展开（一张手风琴） | 可行且干净（同时刻只有一块列表、一条滚动条），但「保存」入口被收起时只剩一行，少一个随时可用的落点 |
| **并排两栏（采用）** | 两栏各自滚，页面不滚；两个方向始终可见；与拖拽天然契合 |

两栏等宽是刻意的：哪一边更宽都在暗示「哪一边更重要」，而它们同等重要。

### 为什么是收藏文件夹，而不是一个「默认展示文件夹」

早期版本只有一个「默认展示文件夹」下拉框。它有两个问题：只有一个值，表达不了
「我常去的是这几层」；而且它叫「默认展示」，听起来像「只能在这一个文件夹里写」——
与右栏的自由导航直接矛盾。

换成 chip 之后：常去的那几层变成一排能一键跳过去的按钮，而「写进哪里」仍然只说眼前这一层。
两个加收藏的入口都是**只有图标的按钮**（☆ 与 ＋）——文案写在 `title` / `aria-label` 上：
chip 才是这一行的主角，两个带文字的按钮加起来能占掉半行，把 chip 挤到看不见。

**「从书签栏里挑一层」是独立组件**（`FolderPicker.ts`），因为它要一个原生 `<select>` 给不了的东西：
**搜索**。候选是完整路径，实测书签栏下有 800+ 个文件夹——一个不能打字过滤、也看不出层级的
下拉框里，用户只能一行行往下找。改成「搜索框 + 可滚动的候选列表」之后，打两个字就能缩到几行
（实测「工具」→ 79 项，再打几个字更少），而 ↑↓ / Enter 能全程用键盘完成。

它的三条取舍：

| 决定 | 理由 |
| --- | --- |
| 绝对定位钉在 chip 栏**右缘**，不用锚点定位 | `anchor-name` / `position-anchor` 要 Chrome 125+，本项目下限 114。对齐右缘而不是对齐按钮：按钮可能靠左（没几个 chip 时），对齐按钮会把面板往左顶出视口，而左溢出不会产生横向滚动条 |
| 已收藏的层**列出来但不可点** | 用户可能就是想确认它在不在；`disabled` 的按钮不派发 click，所以「点不动」是天然行为，不用另写守卫 |
| 超过 200 项只渲染前 200 项，**并如实写一句「还有 N 项」** | 「只剩这些」与「还有更多没显示」是两回事，不能让用户以为已经到底了 |

### 拖拽

拖拽不是另加的功能，而是同一件事的**精确版**：它多了一个维度——**插到哪一格**。
按钮只能「整批送过去」，拖拽能「就这一条、就这个位置」。

| 拖动 | 落到哪 | 行为 |
| --- | --- | --- |
| 左栏一条标签 / 一个分组 | 左栏某一行 | `tabs.move`，并按落点所在行**归组或拆组** |
| 左栏一条标签 / 一个分组 | 右栏 | `writeChildren` 存成书签（落在文件夹行中间就进那一层） |
| 右栏一条书签 / 一个文件夹 / 一种记号 | 右栏某一行 | `bookmarks.move`（同层排序），落文件夹行中间就进那一层 |
| 右栏一条书签 / 一个文件夹 / 一种记号 | 左栏某一行 | 在那个位置 `tabs.create`；文件夹开成一组同名标签 |
| 从**网页**拖来的链接 | 右栏 | 按网址存成书签（零额外代码：载荷就是 `text/uri-list`） |

记号也在表里：**它是一条书签，位置本身就有意义**，所以不是需要特判的特殊行。
拖到左栏时提示「这一条里没有可以打开的网址」（它本来就没有页面可开）。

**拖到自己身上 = 原地不动**，不是「与邻居交换」。这一条单独写代码挡（`moveWindowTabs` 里提前返回）：
`tabs.move` 的 index 是**移动之后**的位置，所以「拖到自己这一行的下缘」会算出「自己 + 1」，
真把标签往后挑一格；而用户看到的是一个他根本没动过的位置。实测：拖到自己下缘 → 0 次 `tabs.move`；
拖到下面那一行的下缘 → 1 次（正确）。

三个实现要点：

1. 载荷带一个自有的 `application/x-tabfurl`（`DRAG_TYPE`）用来区分「内部拖动」与「外部链接」；
   `dragover` 里只能读到 `types` 而读不到 `data`（浏览器的安全限制），
   所以另用一个变量记住「正在拖什么」来决定收不收。
2. **落点用行内三分法**（`spotIn()`）：上缘 = 插到它前面，下缘 = 插到它后面，中间 = **进入**它
   （只对文件夹行与分组行有意义）。三个位置正好对应三种意图，不需要另做「拖到这里就进去」的悬停展开。
3. **两个 move API 的 index 语义是相反的**，写错就是差一格（两边都查了 Chromium 源码确认）：
   - `chrome.tabs.move` 的 index 是**移动之后**的位置（`TabListInterface::MoveTab` 的注释是
     「Moves the tab to index」，而同族的 `MoveGroupTo` 才特意注明「assumes the group has already been removed」）。
     所以算插入位置时要先减掉「原本排在锚点前面、要拖的那几枚」——见 `anchorInsertIndex()`。
   - `chrome.bookmarks.move` 的 index 是**移动前**坐标系里的插入位置
     （`BookmarkModel::Move` 里有 `if (old_parent == new_parent && index > old_index) index--`）。
     所以插到锚点前传锚点下标、插到锚点后传下标 + 1；省略 index 就是追加到末尾。

落点提示分三种，因为三种意图要看得出来不一样：整栏 / 整格用底色或描边，插入用一条线
（`.is-drop-before` / `.is-drop-after`）。插入线用 `box-shadow` 而**不是伪元素**：
记号那一行的横线是**真实元素**（`.marker__rule`，因为 `::after` 永远排在所有子元素之后，
没法把按钮放在线的右边），用伪元素会被两边抢。

**插入的标签也会先卸载**（`discardCommittedTabs`）：拖一个几十枚书签的文件夹过来，
不至于把浏览器同时点燃几十个页面（实测拖一个 7 枚书签的文件夹：创建 7 枚、只留 1 枚加载）。
文件夹开的标签收进一个**同名分组**——「文件夹 ⇄ 分组」本来就是本项目的核心对应关系。

**勾选只有一个维度：一枚标签要么会被还原、要么不会。** 存档行与分组行都是它上面的聚合（三态），
所以不会出现「展开后看着全选、但按钮说没选中」这种自相矛盾。

**两边都默认一个都不勾。**

| 位置 | 默认 | 为什么 |
| --- | --- | --- |
| 保存（窗口 → 书签） | **不勾** | 实际用法是「从这一窗里挑几条存起来」，而不是「整窗收起来再排除几条」；默认全选时几乎每个人都要先取消一大堆 |
| 存档（书签 → 窗口） | **不勾** | 还原是「要打开哪些」，默认全开太危险（可能一下几十个标签页），而且刚存完的不该被下一次还原顺手打开 |

> 早期版本刻意让两侧相反（保存侧全选，理由是「保存的语义就是把当前窗口收起来」），
> 但实际使用下来那个理由不成立：整窗存成书签是个很重的动作，大多数保存只想要其中几条。
> 现在两侧一致，也少了一套「哪边默认是哪种」的心智负担。

两边的**实现**仍然不同，这是被数据结构逼的：

| 侧 | 集合 | 为什么不能换成另一种 |
| --- | --- | --- |
| 左栏 | **选中集**（`windowSelected`） | 默认不选时用排除集，就得在首次渲染时把**当时所有标签**都塞进去，而标签一直在变（新开的没被塞过 → 默认又变成选中）——集合永远追不上窗口 |
| 右栏 | **排除集** + 「见过的书签 id」 | 它的列表会随导航整层换掉；用选中集的话，换一层就得清空重建，而「重渲染不弄丢已做的勾选」这条要求它必须满足 |

顶层、两栏的分组层都反映它下面的实际勾选：

- **顶层按标签聚合**，不按「有几个文件夹还有东西」——否则「已选 4 / 5 枚」会显示成全选。
- **按钮上写数量**（`存过去 (5)` / `打开 (2)`）：得让人在点之前看见这一下会写入或打开多少。
  默认不选时按钮是`存过去 (0)` 且置灰，一看就知道「得先勾几条」。
- **副文案与左栏用同一套嗍词**（`已选 K / N 个标签页` / `已全选 N 个标签页`，这一层一枚都没有时写
  「这一层没有可打开的标签页」）：两边用同一种读法才不会一次一个口径。
  早期版本为了解释「默认不勾」写了一大句「尚未勾选（存档里共 3 枚标签页），勾选后才能打开」，
  它占了半行却只说了一句「现在一个都没勾」，而同一句信息用「已选 0 / 127」就已经说完了。

点击的语义是：全选 → 全不选，部分 / 全不选 → 全选（不沿用原生「把 checked 取反」，
那会让部分状态变成全不选，与惯例相反）。顶层与分组层用同一套规则。

主界面不放在 `src/` 下而放 `pages/`：它不再由清单（`side_panel`）引用，而 `pages/` 正是构建工具
为「未被清单声明的 HTML」设的特殊目录，产物路径即 `pages/app.html`。
它也**不再有共享 chunk**：`shared/commons.js` 只在有两个以上入口时才会被抽出来，
删掉阅读页后就只剩这一个入口，整个共享层并进了 `pages/app.js`（实测 34.8 KB → 41.9 KB）。
所以 `tools/verify-build.mjs` 不再列它——列着就会自检失败，而那并不代表产物有问题。

## 八、关键约定与已知取舍

1. **书签 id 是设备本地的。** 跨设备同步后 id 会变，因此任何持久化数据都不能把书签 id 当作跨设备稳定的标识。现在**唯一**存进设置的 id 就是 `archiveRootId`，重建代价是用户重新选一次文件夹。
2. **同一 URL 可以出现在多个文件夹。** 存档不做去重——多次保存同一个窗口会真的多出几份；写入前也不扫已有内容（扫的话每次保存都多一轮读取）。
3. **分组颜色不往返。** 书签文件夹存不下颜色，还原时分组用浏览器默认色。`TabGroupColor` 只在「空标题分组用颜色消歧」时使用。
4. **写入是逐条 `await` 的。** 一百个标签就是一百次 IPC，第一次保存会有明显停顿。批量优化的预留位置在 `capture.ts` 的 `writeTabs()`。
5. **深色模式**靠 `prefers-color-scheme`，不维护两套主题。
6. **散装书签的位置以「分组的第一个标签」为界。** Chrome 的标签栏里同一分组的标签必定连续，所以窗口总是「未分组段 / 分组 / 未分组段 …」的交替；按 `TabSnapshot.index` 归并就能如实重建这个次序。隐含的另一面是：文件夹层级无法表达「把某个未分组标签插在同一分组的两个标签之间」——但那种布局在 Chrome 里本就不存在。
7. **撤销是内存态的，且顺序不能反。** 没有会话层之后，撤销只能是「删掉这一次新建的书签与分组文件夹」，
   id 在写入时收集（`SaveResult.folderIds` / `bookmarkIds`），**只存在内存里**：关掉界面就失效。
   删除时**先删书签、再删文件夹**：反过来会连书签一起删掉，让后面的 id 全部失效。
   只撤销**最近一次**写入，而不是「这一轮界面里所有写入」——拖拽会让一次会话里出现很多次写入，一次全清会吓到人。
8. **还原时散装书签不建分组。** 早期版本有个「为未分组书签也创建分组」的开关，它会把分散在各处的标签收进同一个 `未分组` 分组，与「保持原位」直接矛盾，已随穿插方案一起移除。
9. **主界面只允许有一个滚动容器，且用满整页宽度。** 主界面是「一屏的应用」：`.app--shell` 把整页锁在一屏内（`100dvh`）
   且不设宽度上限（曾经有一个 `--content-max` 留给阅读页，已随它一起删掉），
   滚动交给两栏各自的 `.box`（`flex: 1; min-height: 0; overflow-y: auto; overflow-x: hidden`）。
   于是顶栏与底部按钮始终在视野里。**不要给列表加 `max-height`**——那会与页面滚动叠成两条滚动条，
   而列表一长，底部按钮就被推出屏幕，得先滚到底才能点（旧版就是 `42vh` / `52vh` 各写一个）。
10. **两栏的 grid 轨道下限必须是 `0`。** `minmax(0, 1fr) auto minmax(0, 1fr)` 里的 `0` 不能省：
   默认的 `1fr` 等价于 `minmax(auto, 1fr)`，那个 `auto` 下限是子项的 min-content 宽度，
   而两栏里都是一列不换行的标题，于是列表的 min-content 就是最长那条标题的宽度
   （实测左栏 422px、右栏 364px）。窗口一窄，两栏之和超过可用宽度，整页就被顶出一条横向滚动条。
   实测 1000px 宽时两栏已经卡在 426/426 不再变窄，900px 起 `scrollWidth` 固定为 918px。
   改成 `minmax(0, 1fr)` 后 480px 宽也不溢出，标题逐级出现省略号。
   `.col` 上的 `min-width: 0` 与 `.box` 的 `overflow-x: hidden` 是同一件事的防御写法——
   后者还顺带避开「竖向滚动条一出现、内容宽度变小，把横向滚动条也激发出来」的连锁。
   （`.box` 的 `overflow-y: auto` 会按规范把另一个轴也算成 `auto`，必须显式写 `overflow-x: hidden` 才能关掉。）
11. **界面层不重写排版。** 字号与间距只有 `base.css` 里的四档字号（`--text-xs/sm/md/lg`）
   与六档间距（`--space-1..6`），不写一次性数字；一行条目的排版（前置控件/图标 + 标题 + 副文案 + 尾部说明）
   用 `.item` / `.item__main` / `.item__title` / `.item__meta`，三处共用。
12. **主界面没有标题块，名字在标签页标题上。** 早期版本在页面上渲染两行 `TabFurl` / `窗口 ⇄ 收藏夹`
   再加一句副标题，那几十像素在两个列表都要用的界面里是最不该花的。名字由 `document.title`（`App.ts`）
   与 `pages/app.html` 的 `<title>` 两处给出——写两遍是因为后者管「脚本跑起来之前」，否则会先闪一下文件名。
   两栏的 `.col__title` 保留（那是栏内标签，不是页面标题）。
13. **内容没变就别重建 DOM。** `refresh()` 在一次动作里会被调好几次（保存、删除、改名、拖一条收藏夹条目…），
   而它每次都会重写整个左栏的 `innerHTML`。用户看到的是一次无意义的整列重绘——实测挪一枚记号时
   「存过去 (N)」会闪一下。现在 `renderWindow()` 先比一个**结构签名**（`windowSignatureOf()`：
   子级顺序 + id + 标题 + 网址 + 固定标记 + 加载状态），相同就只跑 `syncWindowStates()`。
   实测同一个动作里左栏的 DOM 变动从若干次降到 **0 次**。
   同一招已经用在 `FavoriteFolders`（chip 栏比 `id + 标题`、候选下拉框比 `id + 路径`）与右栏的
   面包屑（`lastPathSignature`）上。凡是「由外部数据驱动、又会被频繁重跑」的渲染都该问一句：
   内容没变时能不能什么都不做。**签名的初值必须是 `undefined` 而不是空串**——空列表的签名也是空串，
   一撞就会把「第一次该画空态提示」当成「内容没变」跳过（实测 chip 栏一条都不显示）。
   **勾选不进签名**：它由 `syncWindowStates()` 回填，算进签名就变成「勾一下重绘整列」。
   反过来，**行里画出来的东西一个都不能漏**（漏了 `status`，点「加载」之后那一行不变；
   漏了分组内的 `pinned`，组内标签固定后那个图钉要等到别的变化才出现——两处都是实测踩到的）。

   **拼串交给 `JSON.stringify`，不自己定分隔符。** 手写的分隔符（空格、竖线、控制字符）都隐含
   「内容里不会出现这个字符」这个前提，而标题与网址里什么字符都可能出现。实测：用空格拼时
   `[a, b, a b]` 与 `[a b, a, b]` 拼出了同一个串，该重画的就被「结构没变」跳过去了——错得很安静，
   页面上什么都不报。JSON 的转义是双射、数组结构自己就编码了「几条记录、谁是分组」，
   于是连记录之间的分隔符都不需要。**代价是字段必须显式列出**，而这恰好是我们要的：
   把整份快照直接塞进去会把 `lastAccessed` 也算上，而它每点一次标签就变，
   签名会永远在变，「结构没变就跳过重建」就彻底失效了。

   曾经用**裸控制字符**当分隔符，那还多两层代价，都已实测：ripgrep 见到 NUL 就把整个文件当二进制，
   于是这个文件**从搜索结果里整个消失**（而 `git diff` 照样把它当文本，因为只看前 8000 字节，
   所以症状是「搜不到」而不是「打不开」）；连编辑工具也改不动那一段
   （`oldString` 里写 `\u0001` 传过去是字面 6 个字符，不是那个字符）。
14. **局部的一步操作不要置灰按钮。** `busy` 只当防重入的闩，不要顺手调 `updateButtons()`——
   「置灰 → 恢复」会让中间那排按钮闪一下。真会花时间的操作（保存一整窗、打开几十个标签）才该置灰。
   另外「会出现 / 消失的东西要提前占位」（`visibility: hidden` + `min-height: 1lh`），
   否则一次操作后它们多出一行，会把两栏的高度抽走一点，中间那几个按钮跟着上下跳（实测 9px）。
15. **落在末尾画的是「最后一行下缘的一条线」。** 两栏都用 `markEndDrop(list, pane)`：取该列表所有
   `[data-drop-row]`（含分组 / 文件夹内部的）里的最后一行，只有列表真的是空的才退化成整栏高亮。
   整栏高亮看起来像「丢进这一栏、具体到哪儿我不知道」，而写入其实总是**追加到末尾**，那条线说的才是真话。
   **不能用 `:last-of-type`**：它按元素类型（`li`）算，左栏最后一行的父级是分组里的 `ul`，匹配不到。
16. **数据是异步的，所以列表要先占位。** 设置、标签、书签树三处都是 await 来的，在它们回来之前列表是空的，
   而「空列表」与「真的没内容」长得一模一样——用户看到的是先空一下、内容再蹦出来。
   两个列表面板在模板里就放好了 `.skeleton`，`renderXxx()` 一来就把它冲掉。
   **高度必须与真实行对得上**（同一个 `--row-height`），否则数据到达时列表会「先短一截再变长」。
   脉冲只在 `prefers-reduced-motion: no-preference` 时加。
17. **列表里所有行同一个高度。** `--row-inner`（26px，就是图标方块的高度）+
   `--item-pad-y` × 2 算出 `--row-height`（38px）；`.item` 与 `.marker` 都写 `min-height` 用它，
   骨架占位也用它。文件夹行、书签行、分隔线行、间隔行摆在同一列里，差一像素就看得出「这一行矮一截」。
   推论：**两行文字必须装得进 26px**——13px×1.15 + 11px×1.0 = 25.95 ✔，副文案行高写成 1.1
   就是 27.05，行会被撑到 39px（实测当时左栏每一行都比右栏高 1px）。
18. **左栏由标签事件驱动刷新，而不是只靠「我们的动作自己调 refresh」。**
   `chrome.tabs` 的 `onCreated` / `onRemoved` / `onMoved` / `onUpdated`（只挑 `title` / `url` /
   `groupId` / `pinned` 四个字段）与 `tabGroups.onUpdated` 都接到一个去抖 120ms 的重读。
   触发它的是一个很具体的问题：从收藏夹拖一条到左栏，新建的那枚标签**刚出现时 `url` 可能还没提交**，
   而 `isInternalUrl('')` 会把它当内部页面滤掉——那一轮它就缺席，下一次刷新要等到用户再点别的东西，
   而更早的版本只有「我们的动作」才会刷新，于是它就永远缺席。事件驱动之后拿到提交后 `url`
   的那一轮就会把它补上（实测：外部新建一枚标签，列表自己从 3 条变 4 条）。
   只重读窗口（`refreshWindowOnly()`）：窗口变了不代表右栏要重读一遍。
   **右栏没有对应的事件**（`chrome.bookmarks` 的变更事件在这个扩展里没有接，因为书签树是唯一存储，
   改它的都是我们自己），所以两个面板各备了一个手动刷新按钮（`#window-refresh-btn` /
   `#archive-refresh-btn`，都是只有图标的 `.btn--icon`，**不置灰**——正因为「界面看着不对」才点它）。
   两个按钮都挂在**各自全选框那一行的右端**，两栏位置对称；两个 id 都要写进同一条 CSS，
   而且都要在 `createSelectAll()` 之后 append（按钮靠 `margin-left: auto` 贴右，先插就会把全选框挤到行尾）。
   它们走同一条 `refresh()`；右栏那个不为「只重读书签树」另写一条路径，多一条就多一处会分叉。
   实测：在界面之外（例如书签管理器里）往当前层加一条书签，点右栏的刷新之后列表从 18 变 19，
   全选框的「已选 0 / 281」也变成 282；两栏的按钮右缘都等于各自那一行的右缘（640 / 1384）。
19. **渲染函数的每一条提前返回都要同步勾选状态。** 全选框的文案与三态都算在
   `syncWindowStates()` / `syncArchiveStates()` 里，所以那些 `archiveList.innerHTML = '空态'`
   之后只 `updateButtons()` 的分支必须改成调同步函数——否则全选框会**停在上一次的层**：
   实测从「书签栏」（234 条）进到一个空文件夹时，那一行还写着「已选 0 / 234 个标签页」，
   而列表里明明只有一句「这个文件夹还是空的」。左栏的 `renderWindow()` 有同一个坑。

## 十、工具链取舍

命令速查在 `AGENTS.md`（它每次都会被读），这里只记「为什么这么选」。

**`pnpm watch` 是自己的脚本（`tools/watch.mjs`），只调 `extension build`**，因此产物的权限与生产完全一致。
没有用它自带的 `extension dev --no-browser`，因为两条路都不通（2026-10-02 实测）：

- `extension build` **没有 `--watch`**，真正的监视能力只存在于 `dev` 里。
- `extension dev --no-browser` 确实能只监视不启动浏览器（日志显示 `Chrome (no-browser mode)`），
  但它**必然产出开发版清单**——多出 `scripting` 与 `management` 两个权限并写入 CSP，
  `pnpm verify` 会失败；`--no-reload` 也去不掉这两个权限。

所以监视能力由 `fs.watch` 补（`tools/watch.mjs`，去抖 150ms），而不是换构建器。

**`extension dev` / `start` / `preview` 没有做成脚本**（同为 2026-10-02 决定）：它们都要求先下载独立的
Chrome for Testing（约 150 MB，`pnpm exec extension install chrome`），换来的是浏览器自动加载与热重载；
本项目不做自动化验收，于是换成「`pnpm watch` + 手动点卡片刷新」，省掉一个重依赖。

需要时仍可临时跑 `pnpm exec extension dev`，但要先知道两件事：

1. **它不启动你系统里的 Chrome**，只用托管缓存里的 Chrome for Testing。没装时浏览器起不来，
   而 dev server 会照常打印「ready」并继续挂着——只看这一行容易误判成功。
2. **它会把 `dist/chrome` 覆盖成开发版产物**：清单里多出 `scripting` 与 `management` 权限，
   并写入 `extension-js-control.json`。此时 `pnpm verify` 必然报「权限与预期不一致」。
   所以 **`dev` 之后要再跑一次 `pnpm build`**，才能拿到可自检、可对外分发的干净产物。

**为什么这套取舍值得守**：`pnpm verify` 是本项目唯一能自动拦住「权限悄悄变多」的关卡，
而权限最小化是第 1 条约束（见 `AGENTS.md`）。任何让 `verify` 常态化失败的开发流程，
都会把这个关卡变成「反正它总是红的」——那就等于没有。
