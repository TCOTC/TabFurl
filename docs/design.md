# TabFurl 需求与初步方案

> 状态：骨架阶段。本文是需求范围与数据模型的唯一来源，代码与之冲突时以本文为准；要改范围先改本文。

---

## 一、背景

浏览器自带的收藏夹有两个做不到的地方：

1. **不能把「当前窗口」整套存下来。** 它只能逐个页面手动收藏，标签分组的名字与结构全部丢失，事后无法还原成原来的窗口。
2. **不能同时打开多个收藏文件夹。** 只能在书签管理器里一次次点进去，想并排对比两个分类做不到。

TabFurl 只补这两块。它**不做**通用收藏管理：新增标签、笔记、全文检索、失效链接检测都不在本项目范围内，这些交给浏览器自带的收藏夹（以及用户已有的同步、导入导出能力）。

## 二、目标与非目标

### 目标

| 编号 | 能力 | 说明 |
| --- | --- | --- |
| F1 | 窗口 → 书签（可选范围） | 把当前窗口的标签按标签分组存成一棵书签文件夹子树，每次保存产生一个带时间戳的会话文件夹。保存前可以逐枚勾选要保留哪些标签，整组也可以一键勾掉 |
| F2 | 书签 → 窗口（可选范围） | 打开一个存档文件夹，按它的**子文件夹（一层）**创建对应的标签分组；也可以逐枚勾掉不想打开的标签，或选择只开标签页、不建分组 |
| F3 | 文件夹启动器 | 勾选多个存档文件夹，各开一个阅读页标签页，用于并排浏览不同分类 |
| F4 | 存档管理 | 列出存档根下的全部会话，支持搜索、展开／折叠、重命名、删除（两步确认） |
| F5 | 撤销 | 撤销最近一次保存（删除刚建的那棵子树） |
| F6 | 零网络 | 不申请任何 `host_permissions`，不发任何外部请求 |

### 非目标

- 标签、笔记、多维归类（那是另一个产品）
- 双向实时同步（三方状态冲突的成本远高于收益）
- 与思源等外部笔记软件的集成
- 自建存储：**书签树是唯一存储**，不引入 IndexedDB

## 三、书签树数据模型

```
📁 标签页存档                    ← 存档根：用户在书签栏里指定的一个已有文件夹
   └── 📁 2026-10-02 14:30      ← 会话文件夹（一次保存 == 一个）
          ├── 📁 工作            ← 标签分组（分组标题原文）
          │      ├── 🔖 标题 A
          │      └── 🔖 标题 B
          ├── 🔖 标题 C          ← 窗口里没进分组的标签，就地放成散装书签
          └── 📁 阅读
```

两条结构规则：

- **存档根是书签栏里的一个已有文件夹，由用户在「设置」里指定。** 扩展不建文件夹、不往「其他书签」里写任何东西，
  存档直接写进选中的文件夹。代价是「选中文件夹下的每个子文件夹都会被当成一次存档」，
  所以设置面板会提示专为存档建一个文件夹。
- **直接子级严格按窗口顺序排列。** 标签分组建成了子文件夹，窗口里没进分组的标签建成散装书签，**插在它们原来的位置上**——不会被集中挪到末尾，也不会有「未分组」这一层。窗口里一个分组都没有时，结果就是一列散装书签，所以「保存 → 还原」始终是对称的。
- **会话文件夹永远在存档根的直接下级。** 层级最多三级（会话 → 分组 → 书签），与 Chrome 标签分组不支持嵌套这一点保持一致。

## 四、命名规则

命名只在 `src/shared/naming.ts` 里实现，界面层不得自己拼字符串。

| 层级 | 规则 | 示例 |
| --- | --- | --- |
| 存档根 | **不由扩展命名**：用户在书签栏里指定一个已有文件夹 | `标签页存档` |
| 会话 | 可选自定义名 + `YYYY-MM-DD HH:mm`（本地时间，零填充）；名字留空时只用时间戳 | `会议 · 2026-10-02 14:30` |
| 分组 | 分组标题原文 | `工作` |
| 空标题分组 | `未命名分组（蓝）`，用颜色消歧 | `未命名分组（蓝）` |

> 上表就是**写进书签的实际形态**：`sanitizeFolderName` 只做控制字符、空白与长度这三件事，
> 不动任何可打印字符（见下面的清洗规则），所以时间戳里的冒号就是冒号，用户手打的名字也按原样存。

**自定义名放在时间戳前面**（`名字 · 时间戳`），因为名字是用户自己挑的，扫列表时先看到它更快。
代价必须说清楚：**存档多了以后是按名字排序，而不是按时间**。早期版本用「时间戳 + 站点后缀」的
`时间戳 · 站点` 形态，那时日期前缀是排序保险；现在名字占了首位，这条保险只在名字相同的会话之间生效。

**名字不与时间戳争长度**：名字单独按预算截断（`MAX_FOLDER_NAME_LENGTH` 减去时间戳与分隔符），
而不是把拼好的整串一起截——否则名字一长，截断就会把末尾的时间戳切掉，那是唯一的排序依据。

**自定义名不跨会话记忆**：输入框默认置空，保存后清空。没有「窗口自定义命名」这回事——
`chrome.windows.Window` 根本没有 `title` / `name` 字段，Chrome 也不提供给窗口命名的功能；
想做「按窗口记名字」只能由扩展自己用 `windowId` 索引（而 `windowId` 重启后就变），所以没做。

**为什么要保留时间戳**：`bookmarks.create()` 不传 `index` 时追加到末尾，所以同一个浏览器内
不加时间戳也能保持创建顺序；但跨设备同步、手动拖动排序、导出到别的工具之后顺序不再保证。
时间戳是排序与去重的保险，代价只是名字长一点。

**清洗规则**（`sanitizeFolderName`）：

1. 去掉控制字符（`\u0000-\u001f`、`\u007f`）
2. 折叠连续空白为一个空格，并去掉首尾空白
3. 截断到 100 字（截断处再去尾随空白）

**可打印字符一律保留原文**，包括 `/ \ : * ? " < > |`。Chrome 不禁这些字符（`create()` 的
`title` 就是个普通字符串，官方文档没写任何禁用字符或长度上限），所以不做替换。
早期版本会把它们换成 `_`，那是为「导出为文件路径」提前挡 Windows 的非法字符；
**那个功能没有做，规则随之删掉**（依据：不为没实现的功能付出改名的代价）。
真要做导出时再补，届时还得处理 Windows 的保留设备名（`CON`、`NUL`、`COM1`……）与不能以点结尾两条。

**重名不覆盖**：`dedupeName()` 在末尾追加 ` (2)`、` (3)`……绝不合并、绝不覆盖。

## 五、还原规则

| 输入 | 行为 |
| --- | --- |
| 子文件夹 | 建一个同名标签分组（关掉「建分组」时跳过这一步） |
| 子文件夹里的书签 | 打开标签并归入该分组 |
| 会话文件夹顶层的散装书签 | 打开成**未分组**的标签，位置按它们在文件夹里的次序 |
| 被勾掉的书签 | 不打开；因为它而空掉的分组也不创建 |
| 子文件夹里的**子文件夹** | **跳过**（只处理一层），数量计入 `skipped` 并在界面显示 |
| 浏览器内部页面 | 跳过，计入 `skipped` |

因为恢复时是**按会话文件夹的子级顺序**依次开标签的，还原出来的标签次序与保存时一致：未分组的标签会回到它们原来的位置，而不是被堆到末尾。

还原目标窗口可选「新窗口」或「当前窗口」。新窗口通过第一个标签顺手创建，避免先开空窗口再补标签的闪烁。

`groupTabs: false` 是「只开标签页」：同一份计划，只是不建分组（子文件夹的名字丢掉）。

**打开的标签默认不加载**（懒加载）。

`chrome.tabs.create()` **没有**「先不加载」这个选项——传了 `url` 就会立即开始加载，
`active: false` 只是不聚焦，所以一次还原几十个标签会造成瞬时并发加载而卡顿。
真正能做这件事的是 `chrome.tabs.discard()`（Chrome 54+）：从内存卸载，但标签仍在标签栏上
（标题、位置、标签分组都保留），点开时才重新加载。

三条实现要点：

1. **舍弃必须放在建分组之后**。分组、窗口都完成了，标签的位置与归属已固定，此时卸载最安全。
2. **活动标签无法被舍弃**（API 限制：`tabs.discard` 对活动标签不生效），所以每个窗口会留一枚已加载的。
   这正好让人看得见窗口确实开出来了。
3. **舍弃失败不能拖垮整次还原**：标签已经打开了，只是会真加载而已，所以逐个 `try/catch` 只记日志。

状态栏会明说「其中 N 个未加载（点开才加载）」，否则用户看到一排灰标签会以为还原出错了。

**勾选与计数共用一条通路。** 界面渲染的清单与还原用的计划都是 `restore.ts` 的 `planRestore()`，
界面再把勾掉的书签 id 交给 `applyExclusions()`；所以「看到几枚就会开几枚」不靠人工对齐，而是同一份数据。

## 六、平台与权限

**目标浏览器只有 Chrome**（最低 114，写在 `minimum_chrome_version`）。不做 Firefox 兼容。

这带来了实质简化，不是单纯的偷懒：

- `chrome.tabGroups`（89+）可以直接调用，**不需要特征检测与降级分支**。
- MV3 下 `chrome.*` 原生返回 Promise，**不需要 `webextension-polyfill`**，也不需要维护 `browser.*` / `chrome.*` 两套类型。
- 清单是纯 MV3，**没有任何 browser-prefixed 字段**，减小了一半（含 `browser_action` / `sidebar_action` 的 MV2 形态）。

| 权限 | 用途 |
| --- | --- |
| `bookmarks` | 读写书签树 |
| `tabs` | 读取标签标题 / URL / 分组，创建标签 |
| `tabGroups` | 读取分组标题与颜色、创建分组 |
| `storage` | 保存设置 |
| `favicon` | 用 `_favicon` 端点取网站图标；**读 Chrome 本地缓存，不发网络请求**。已申请 `tabs`，所以它不额外产生权限警告（官方文档明确：只有尚未申请 `tabs` 或主机权限时它才警告） |
| `host_permissions` | **无** |

图标就一张真图标（22px），没有底色或首字母。`_favicon` 的实测行为（2026-10-02 在真实 Chrome 里验证）：
**它从不失败**——缓存里有就返回真图标，没有就返回**默认地球**，连根本不存在的域名也返回 32×32 的图片
（`onerror` 不触发）。所以代码里不需要失败处理：产物要么是真图标、要么是地球，不会出破图。
代价要说清楚：**没有图标的站点会长成一个样**，一排全是地球。
不请求 Google 的 favicon 服务，也不把 `tabs.Tab.favIconUrl` 拿来渲染——后者指向网站服务器，
渲染时等于向该站点发请求。

> 如果将来要支持 Edge / Brave 等 Chromium 内核浏览器：不用改代码，直接加载 `dist/chrome/` 即可（它们共用同一套 API）。只有要支持 Firefox 才需要重做上面这几层。

## 七、模块划分

```
src/shared/         与界面无关的核心，全部可独立复用
  types.ts        领域类型 + 默认设置
  naming.ts       命名规则（纯函数，无 IO）
  urls.ts         URL / 主机名 / 占位块小工具
  bookmarks.ts    书签树读写与展开
  capture.ts      窗口 → 书签（F1）
  restore.ts      书签 → 窗口、文件夹启动器（F2/F3）
  settings.ts     chrome.storage 读写
  tile.ts         占位块 HTML 生成
  base.css        设计变量与基础组件

src/app/            主界面的界面模块（只被 pages/app.ts 引用）
  App.ts          标签页外壳：顶部三个 Tab、面板装配、跨面板刷新
  CapturePanel.ts 保存面板
  ArchivePanel.ts 存档面板
  SettingsPanel.ts 设置面板
  dom.ts          面板契约（Panel / AppEvents）与共用小工具
```

依赖方向单向：`pages/` → `src/app/` → `src/shared/`。**`shared/` 不得 import 任何界面模块**；
三个面板之间也不互相 import，只通过 `AppEvents` 通信（谁该刷新由 `App.ts` 决定），免得绕成环。

界面只有一个页面（外加阅读页）：

- `pages/app.html` —— 主界面，点工具栏图标以**独立标签页**打开（已开着则切过去，不重复开）。
  顶部三个标签页切换（hash 可直达：`#capture` / `#archive` / `#settings`），每个标签页是一块面板：
  - **保存**：按窗口顺序列出标签（分组是带缩进的块，未分组的标签就地在原位），逐枚勾选要保留哪些；保存与撤销。**默认全选**。
  - **存档**：会话树（会话 → 分组 → 标签），支持搜索、全部展开／折叠、批量打开，以及逐项的改名与删除。

**勾选只有一个维度：一枚标签要么会被还原、要么不会。** 存档行与分组行都是它上面的聚合（三态），
所以不会出现「展开后看着全选、但按钮说没选中」这种自相矛盾。

**两边的默认值相反，这是刻意的：**

| 位置 | 默认 | 为什么 |
| --- | --- | --- |
| 保存（窗口 → 书签） | **全选** | 保存的语义就是「把当前窗口收起来」，少数不想存的手动取消 |
| 存档（书签 → 窗口） | **全不勾** | 还原是「要打开哪些」，默认全开太危险（可能一下几十个标签页）；且存完的新存档也不会被下一次还原顺手打开 |

存档侧仍然用**排除集**而不是选中集，配合一份「见过的书签 id」：没见过的默认算排除。
这样既做到「默认不勾」，重渲染又不会弄丢用户已做的勾选（换成选中集会两头都不讨好）。

顶层、存档、分组三层都反映它下面的实际勾选：

- **顶层按标签聚合**，不按「有几个存档还有东西」——否则「已选 4 / 5 枚」会显示成全选。
- 搜索过滤时，三态框与打开目标都只算**列表里可见的**，文案会明写「仅列表可见」，
  避免出现「按钮写着 12 个存档、实际只开了 3 个」这种对不上。
- **打开按钮上写数量**（`还原为窗口（247 个标签页 / 12 个存档）`）：得让人在点之前看见这一下会打开多少。
- **会话行副文案以「已选」为主**：存档侧默认不勾，若把「还会还原的枚数」直接写成「N 个标签」，
  默认会显示成「0 个标签」，看着像这个存档是空的。现在写作 `未勾选 · 共 5 枚标签` / `已选 2 / 5 枚标签` / `已全选 5 枚标签`。

点击的语义是：全选 → 全不选，部分 / 全不选 → 全选（不沿用原生「把 checked 取反」，
那会让部分状态变成全不选，与惯例相反）。三层都用同一套规则。
  - **设置**：存档根选择（书签栏内的文件夹）、还原行为。
  主界面不放在 `src/` 下而放 `pages/`：它不再由清单（`side_panel`）引用，而 `pages/` 正是构建工具
  为「未被清单声明的 HTML」设的特殊目录，产物路径即 `pages/app.html`。
- `pages/folder.html` —— 文件夹阅读页，由 `?id=<folderId>` 指定文件夹；与主界面同属 `pages/` 特殊文件夹机制。

## 八、关键约定与已知取舍

1. **书签 id 是设备本地的。** 跨设备同步后 id 会变，因此任何持久化数据都不能把书签 id 当作跨设备稳定的标识。当前只有 `archiveRootId` 与 `lastSessionFolderId` 存了 id，且都能重建（前者重建代价是用户重新选一次文件夹，后者丢了只是少一个「撤销」）。
2. **同一 URL 可以出现在多个文件夹。** 存档不做去重——去重的语义在「套用窗口结构」这个前提下是错的。
3. **分组颜色不往返。** 书签文件夹存不下颜色，还原时分组用浏览器默认色。`TabGroupColor` 只在「空标题分组用颜色消歧」时使用。
4. **写入是逐条 `await` 的。** 一百个标签就是一百次 IPC，第一次保存会有明显停顿。批量优化的预留位置在 `capture.ts` 的 `writeTabs()`。
5. **深色模式**靠 `prefers-color-scheme`，不维护两套主题。
6. **散装书签的位置以「分组的第一个标签」为界。** Chrome 的标签栏里同一分组的标签必定连续，所以窗口总是「未分组段 / 分组 / 未分组段 …」的交替；按 `TabSnapshot.index` 归并就能如实重建这个次序。隐含的另一面是：文件夹层级无法表达「把某个未分组标签插在同一分组的两个标签之间」——但那种布局在 Chrome 里本就不存在。
7. **还原时散装书签不建分组。** 早期版本有个「为未分组书签也创建分组」的开关，它会把分散在各处的标签收进同一个 `未分组` 分组，与「保持原位」直接矛盾，已随穿插方案一起移除。

## 九、待决问题

| 问题 | 备选 |
| --- | --- |
| 还原时分组颜色 | 保持默认色 / 按调色板循环分配 |
| 深层嵌套（子文件夹的子文件夹） | 继续跳过 / 递归平铺进同一分组 / 建二级分组（Chrome 不支持嵌套分组，只能平铺） |
| 阅读页是否也要逐枚勾选 | 现在只有主界面能逐枚勾选；阅读页还是整文件夹还原 |
| 要不要支持多窗口 | `chrome.tabs.query({currentWindow: true})` 取的是**主界面所在窗口**，其他窗口看不见 |

> 已决：「是否加 `favicon` 权限」已定为**加**。当初挂在待决里的理由是「需要权衡权限提示语变长」，
> 但该前提是错的——`tabs` 已经在权限集里，而 `favicon` 只在尚未申请 `tabs` 或主机权限时才触发警告，
> 所以加载该权限不会让权限提示语多出一句。

## 十、开发命令

```bash
pnpm install
pnpm build        # → dist/chrome/（同时生成 extension-env.d.ts）
pnpm dev          # 同上，但不混淆：单次开发用构建；只构建，不启动浏览器
pnpm watch        # 监视 src/ 与 pages/，改完自动重建（日常开发用这个）
pnpm test         # 单元测试（node:test；需要 Node >= 23.6）
pnpm typecheck    # 构建不做类型检查，必须单独跑，且需先 build
pnpm verify       # 产物自检：权限漂移 / host 权限 / Firefox 残留 / 入口缺失 / 中文编码 / 测试文件泄漏
pnpm icons        # 重新生成占位图标
```

加载进 Chrome：`chrome://extensions` → 开启开发者模式 → 「加载已解压的扩展程序」→ 选 `dist/chrome`。
`pnpm watch` 重建后，点扩展卡片上的刷新（↻）再重开主界面标签页。

`pnpm watch` 是自己的脚本（`tools/watch.mjs`），只调 `extension build`，因此产物的权限与生产完全一致。
没有用它自带的 `extension dev --no-browser`，因为那条路必然产出开发版清单（多出 `scripting` 与
`management` 权限），会破坏权限最小化。

`extension dev` / `start` / `preview` 没有做成脚本：它们都要求下载独立的 Chrome for Testing（约 150 MB），
而换来的是热重载与一套控制桥；本项目不做自动化验收。需要时临时跑 `pnpm exec extension dev`，
但注意它会把 `dist/chrome` 换成开发版清单（多出 `scripting` 与 `management` 权限），跑完要再 `pnpm build`。
